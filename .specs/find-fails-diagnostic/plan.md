# Make find-fails investigate and explain tool failures

## Objective

Make `/find-fails` start one bounded diagnostic turn in the active Pi session that automatically investigates at most three custom-tool failures, may record only the evidence-proven outcomes authorized in this plan, explains what happened in plain language, and stops without fixing code.

## Completion Evidence

- Evidence: A representative command run refreshes one local DuckDB read model from append-only session and decision JSONL, selects no more than three undecided, due, changed, or regressed candidates, and starts one active-session diagnostic turn with only bounded failure/repository inspection and a narrow decision writer. Each finding leads with one verdict word - `Failing`, `Fixed`, `Expected`, `External`, or `Unresolved` - followed by `Last seen: M/D/YYYY h:mm:ss AM/PM` in the user's local time and one concise explanation linking the failed workflow to the observation and proof needed for that verdict. Tests prove expected and addressed candidates stay suppressed until revisit, fingerprint change, or post-effective recurrence; stale, contradictory, and incomplete evidence remains unresolved; cancellation and malformed input fail clearly without corrupting evidence; and the command no longer invokes Python or an isolated shortlist model.
- Fails when: `/find-fails` asks for intermediate shortlist approval, investigates more than three candidates, changes repository files, uses multi-word or internal ledger labels as the human verdict, omits the last-seen local timestamp, treats an old observation as proof of a fix, dismisses a candidate from counts or model confidence alone, mutates source session JSONL, exposes unrestricted repository reads, maintains competing Python and TypeScript tool-failure authorities, reports assumed future-scan behavior, starts more than one provider turn, invents response options when no action remains, or leaves its tool restriction active after the diagnostic turn settles.

## Boundaries

- In scope: `pi/extensions/tool-failure-triage.ts`; new focused TypeScript modules under `pi/lib/` for the DuckDB read model, deterministic candidate state, bounded inspection, active-turn authority, report semantics, and locked decision append; Pi package metadata; focused Pi tests; removal of migrated Python tool-failure scan/report/decision code and tests after parity; and the owning Pi log-analytics and observability contracts.
- Out of scope: General-purpose `pi/analytics/pi_log_query.py` queries and non-tool-failure views; session/history JSONL formats; unrelated diagnostics; automatic code fixes; generic transcript redesign; DuckDB migration outside `/find-fails`; or adversarial review during normal command execution.
- Preserve: Session JSONL and decision JSONL as append-only authoritative evidence; the local-private decision path and existing candidate fingerprint meaning; custom-extension-only filtering; explicit provider-boundary disclosure; TUI cancellation and immediate feedback; bounded and redacted provider evidence; current ledger precedence, revisit, changed-fingerprint, and post-effective-regression behavior; unrelated `pi/AGENTS.md` changes already present in the primary worktree; and the Python analytics helper for unrelated log analysis.
- Assumptions: `@duckdb/node-api` remains installable for Pi's supported Windows x64, Linux x64/arm64, and macOS x64/arm64 runtimes; one cached instance owns each disposable database path per process; the user-approved automatic-decision categories in this plan become explicit current authority in the owning contract; and `/do-it` stops rather than retaining a Python runtime fallback if the first supported-platform slice fails.
