# Simplify development to prompt-guided planning and execution

## Objective

Remove the custom development-process controllers and conflicting instructions while retaining planning, execution, and goals in worktrees by default, existing execution flags/defaults, adversarial planning review, and useful parallel subagents. The agent captures intent, asks about consequential gaps, understands affected behavior early, implements, tests, diagnoses failures and works to completion. Damage control and `/commit` remain unchanged.

## Completion Evidence

- Evidence: Each planning/execution command has one authoritative instruction body and one command entrypoint. Ordinary planning, review and implementation do not require a lifecycle, readiness receipt, mandatory task graph, generated condition mapping, or generic repair allowance. Only necessary flag/target/session transport remains in code; no replacement development state machine or simplicity mode is introduced.
- Evidence: Existing execution flags, combinations and defaults pass focused contract tests. Planning, execution and goal work default to worktrees, honor an explicit in-place request, and reuse the selected worktree for the same work. Default execution starts a fresh session and, after verified completion, archives applicable plans, commits, merges and cleans up. Existing exceptions retain their meaning.
- Evidence: Revised instructions preserve user intent, ask rather than invent consequential decisions, investigate affected features/callers/external interfaces before building, use adversarial review to find omissions, divide work into simple real dependencies suitable for useful parallel subagents, integrate results and respond to failures without universal development retry counters. Review remains an activity, not a runtime certificate.
- Evidence: Focused tests cover retained command/session/worktree behavior, goal continuation, and protected commit/damage-control behavior; affected TypeScript compiles. Incomplete work, explicit live limits, actual authority and unrelated resources remain protected.
- Fails when: Old process gates survive behind new prompts; flags/defaults change or silently stop working; work executes in the wrong target; intent/partial work is lost; useful parallel execution disappears; commit/damage-control behavior changes; or new guidance recreates the retired procedure.
- Limits: Direct content review establishes the authored instructions, not guaranteed future model judgment. Deterministic tests exercise actual host/operation behavior with controlled inputs, not a child model choosing the right action. No live-model benchmark, timing target, exhaustive certification or new policy-enforcement framework is required.

## Accepted behavior

- Worktrees: Planning, execution and goal work happen in a worktree unless the operator requests otherwise. Reuse the selected worktree across planning, implementation and continuation of the same work. Planning alone leaves the plan/worktree available for implementation; it does not merge unimplemented work. This explicitly changes the current primary-only planning default.
- Execution defaults: Preserve fresh-session execution, worktree isolation, and automatic archive/commit/merge/cleanup after successful implementation. Raw work has no plan to archive. Existing plan-selected commit-and-retain behavior remains supported.
- Flags: Preserve `--no-clear` (same session), `--in-place` (no additional worktree), `--no-merge` (archive applicable plan and commit, retain unmerged worktree/branch), their independent combinations, and `--` (remaining input is literal). Preserve rejection of duplicate or unknown leading execution options. With `--in-place`, no-merge is redundant and no other worktree is created, merged or removed. No-merge overrides a plan's default merge closeout. Do not invent new names for existing options.
- Planning and goal controls: Preserve `plan-it quick` as an explicit review-skipping option, and foreground/unattended goal start, status, stop and resume. Normal planning includes adversarial review. Use `--in-place` for the newly requested non-worktree option on planning/goal too; this extends applicability, not the existing flag's meaning. Planning accepts optional leading `quick`, then `--in-place`, then optional `--` and the request. Goal start accepts `--unattended` and `--in-place` in either order before its objective; only bare unflagged `status`, `stop`, or `resume` are control operations. Repeated recognized start flags are errors; unrecognized goal/planning input retains its current treatment as request text rather than acquiring execution's stricter unknown-option rule. After `--`, do not reinterpret flag-like text or control words. Preserve existing command trimming, while retaining the original invocation/file text for exact intent; do not promise new byte-preserving CLI tokenization.
- Simplification: Remove mandatory planning lifecycle/review tracking, plan-format certification, mirrored plan/task/goal completion representations, development repair counts and automatic quality-repair/settlement ceremony. Keep a plan/task when it helps preserve actual work, not as permission to act. Keep useful subagents and their real execution/results/cancellation/containment; do not redesign the subagent platform.
- Instructions: Preserve technical knowledge and independent safety rules. Replace development-flow prescriptions rather than adding exceptions. Future work uses relevant checks and diagnosis-led repairs, not a universal late-only schedule or one-repair budget. This transition itself follows the currently required final-batch execution policy below.

## Mechanism and source contracts

Keep instructions as the source of development behavior. Native prompt templates are suitable when no host action is needed. Preserving automatic fresh-session execution requires a small host adapter because `ExtensionCommandContext.newSession` is command-only; a Markdown template cannot itself perform that operation. Retain only option parsing, selected target/worktree preparation, exact intent/session handoff and prompt dispatch in that adapter. No task execution engine, review registry, readiness checks, repair scheduler or closeout certificate belongs there.

Use one instruction body per command, not duplicate native and extension registrations. Planning/execution bodies can remain rewritten files under `pi/skills/workflow/`, loaded by the minimal host adapter; moving them to `pi/prompts/` is unnecessary if it creates a competing command. Ordinary conversational planning and execution use the same instruction bodies and operations. Where the agent needs a host-only start/session action, expose one thin callable start adapter sharing the command path, not a second runner. Use existing Pi session/dispatch facilities; do not add a general-purpose framework.

Retain useful existing worktree/Git helpers with actual target and preservation checks. Planning creates/reuses the existing worktree ownership record keyed by repository and plan slug, with its existing `planPath`, branch and selected worktree fields. Write the future plan directly inside that worktree; do not introduce a primary-copy synchronization requirement. Execution/goal lookup consults that record before creating another tree, including when invoked from the primary checkout. `assertOwned`/`ensureWorkflowWorktree` already support transfer from a `plan-it` owner to `do-it`/`goal`; preserve that operation without readiness gates. In-place work reuses the existing in-place identity representation, extended only as necessary for planning/goal. Existing primary-authored plans retain their current non-overwriting transfer path.

Closeout remains model-directed ordinary Git work, as it already is for archive/commit/merge. Instructions name the selected repository/branch, archive only completed applicable plans, commit in-scope work, inspect Git state, merge only under merge policy, verify ancestry/result, and remove only the identified merged worktree/branch. Under no-merge, retain the committed branch/worktree. Recovery inspects the original plan/archive, Git HEAD/ancestry, worktree registration and existing ownership data to determine the unfinished operation; it never reruns implementation merely because the source plan was archived. Reuse existing target/cleanup helpers and the unchanged commit capability. Do not add a new all-in-one transactional closeout tool or retain `plan_archive`/`workflow_complete` certification. Multi-command Git closeout is not atomic and is not being promised as such.

Cancellation returns before teardown; creation/setup failure may throw after replacement has begun and is not a rollback guarantee.
