# Plan: Primary-Owned Planning and Goal Lifecycle

## Context

The completed Fable orchestration work now keeps the selected primary model as the root orchestrator by default, removes implicit `orchestrator` promotion, and preserves explicitly requested non-Fable coordinators. The existing `/goal` lifecycle already persists unattended plans, root-task links, validation evidence, recovery state, and resume reconciliation, but a generated goal still starts from one generic T1 task. `/plan-it` writes a draft and asks the operator to invoke `/review-it` separately.

Repository research in `.specs/pi-workflow-refinement/notes.md` favors deterministic control for stable transitions, model judgment for plan quality, and evidence-based reviewer selection rather than a fixed large panel. Follow-up workflow review found repeated requests to remove overengineering and repair missed plan gaps, together with an explicit rejection of repeated panels, post-repair panels, vague progress labels, and treating an actionable failure as a reason to stop. A live expert fan-out also exposed a runtime-generation mismatch: a newer tree client received an older process-global broker response without permit credentials.

## Objective

One primary-owned lifecycle must create an execution-ready reviewed plan, materialize its required durable root tasks, execute and recover across context compactions, report concrete state, verify completion, and archive the completed plan without requiring the operator to chain `/plan-it`, `/review-it`, and `/do-it` manually. After the lifecycle changes settle, the same plan must determine whether any small evidence-based Fable or subagent prompt-cache correction is justified and otherwise leave caching behavior unchanged.

## Boundaries

- In scope: primary-owned subagent scheduling across compatible reloads, proportional bounded plan review, `/plan-it` and `/review-it` responsibilities, one canonical plan and task graph per unattended or explicitly planned foreground goal, direct ordinary foreground goals, typed actionable-failure recovery, concrete terminal reporting, plan archival, focused lifecycle tests, one isolated command smoke, owning documentation, and one bounded post-integration assessment of existing Fable and child prompt-cache behavior.
- Out of scope: worker survival after the Pi process exits, a durable external scheduler, provider-hosted multi-agent orchestration, removing explicitly requested non-Fable coordinators, changing Fable subscription-only enforcement, a general workflow framework, mandatory review panels for low-risk work, new cache telemetry, repair of unrelated analytics dependencies, multi-plan goal transactions, UX guidance, paid live model calls without existing authorization, changes to installed Pi or `node_modules`, pushing commits, or unrelated command redesign.
- Preserve: the selected primary model owns orchestration, adjudication, and readiness; leaves cannot delegate; Fable dispatches subscription leaves only; non-Fable roots may explicitly request a coordinator; task records remain root-owned; live child trees remain process-local; interrupted modifying work is never blindly replayed; damage-control and live-incident boundaries remain authoritative; `/review-it` remains available for explicit review of plans, PRDs, and other artifacts.
- Assumptions: explicit coordinator support remains an advanced compatibility path, while ordinary planning, review, and goal work uses direct root-to-leaf dispatch. Foreground goals remain interactive and session-owned rather than becoming detached jobs. Full process failure reconciles the canonical plan, durable tasks, and goal mapping after resume rather than recovering live child processes.

## Cache Evidence and Decision Rule

- `PI_CACHE_RETENTION=long` is already configured by the shell profiles, and spawned children inherit `process.env`.
- Pi 0.84.1 Bedrock Converse automatically places cache points at the system prompt and final user message for `amazon-bedrock/us.anthropic.claude-fable-5`; long retention requests a one-hour TTL.
- `bedrock-mantle/anthropic.claude-fable-5` uses Pi's Anthropic Messages adapter, which already applies `cache_control` at stable prompt boundaries.
- OpenAI Responses requests 24-hour prompt-cache retention where supported. Child session IDs are unique and currently become the OpenAI `prompt_cache_key`, so otherwise stable prefixes may receive weaker cross-child reuse.
- `pi/extensions/fable.ts` appends fixed orchestration instructions. `pi/extensions/subagent/index.ts` passes the stable agent prompt through `--append-system-prompt` and sends the task as the user message. Existing subagent and orchestration usage records already include `cacheRead` and `cacheWrite`.
- Fable routes children to OpenAI Codex subscription models. Improving child cache reuse therefore affects subscription-model efficiency rather than directly reducing Bedrock dollar spend.
- The default decision is no code change. A local change is justified only by a demonstrated defect whose expected reuse offsets long-cache write premiums. A prompt cache key independent from child session identity remains a separate upstream proposal unless the current extension API supports it directly and safely.

## Requirements Contract

- R1: The selected primary model must own orchestration, reviewer selection, adjudication, plan content decisions, and readiness for normal planning and goal execution. Reviewers and implementation workers are leaves, return bounded results, and never spawn other workers. Plan writes are serialized: the primary writes when it has file tools; otherwise one scoped modifying leaf may perform the primary's chosen draft or repair while reviewers remain read-only.
- R2: Direct root-to-leaf work must use a captured in-process broker and must not call `listen()` or make a TCP round trip to the root's own broker. Remote coordinator requests must present the matching protocol and runtime generation before permit acquisition or child spawn. An incompatible broker with active or queued work must remain intact and reject cross-generation dispatch until that work settles. Once the incompatible broker is idle, the next root invocation must retire and replace it atomically in-process without requiring a Pi restart. Invocation cleanup must use its captured broker rather than reacquire the global singleton, and no recovery path may silently replace an active broker.
- R3: Every `/plan-it` invocation must receive a primary reread and deterministic plan-contract validation. Reviewer delegation is required only when the primary records a material risk such as a cross-boundary runtime change, live or stateful mutation, security or safety control, or disputed feasibility. A material-risk review uses one adversary plus either one feasibility proponent for a distinct disputed claim or one domain specialist for domain evidence. It never exceeds two reviewers, one round, or one perspective per concern. Low-risk plans do not launch a panel.
- R4: The primary must verify outcome-changing reviewer claims, classify them as required repair, rejected or deferred advice, or an unresolved operator decision, and apply at most one coherent repair pass. A failed reviewer may be retried once only for that perspective and only with a materially changed strategy; otherwise the workflow may continue only when remaining evidence covers that perspective. After repair, the primary or a read-only leaf when the primary lacks inspection tools must reread the result, and deterministic plan-contract validation must pass. The workflow must not rerun healthy reviewers or create review directories, reviewer ledgers, debate transcripts, a synthesis worker, or a second panel.
- R5: `/plan-it` may use only a command-specific lifecycle with the states needed to prove draft, risk selection, settled review, adjudication, repair or acceptance, post-repair inspection, and readiness; it must not introduce a general workflow engine. A narrow `plan_progress` control tool records bounded transitions for the active invocation, persists a compact snapshot in Pi session entries for compaction and resume, and validates the canonical plan before readiness. It stores role, outcome, disposition, and repair state, not reviewer prose or separate artifacts. Fable may call this control tool while delegating serialized file I/O to one scoped writer. `/review-it` remains a prompt-backed generic artifact review command using the same proportional evidence and repair rules, but successful `/plan-it` does not hand the operator to `/review-it` before execution.
- R6: Unattended goals have exactly one reviewed canonical plan. The plan is the source specification for unique task keys and `Depends on` edges; parsing must reject duplicate keys, missing dependencies, self-dependencies, and cycles. Existing task-batch `blockedByKeys` materializes the runtime graph, the task registry is authoritative for scheduling, and `goal.items` stores only the plan-key-to-task-ID mapping plus attempt state. Tasks are stamped with goal ID, canonical plan path, and plan task key so partial creation or linking can be reconciled idempotently. Every required unattended task must be linked before modifying work begins. Foreground goals remain interactive and direct by default; they use a reviewed canonical plan only when one is explicitly supplied or material risk or ambiguity requires it, and any foreground plan state must survive compaction, compatible reload, and explicit session resume without becoming a detached loop.
- R7: After an observed non-success, execution must record a typed outcome before proceeding. `error`, `inconclusive`, `schema_invalid`, `verifier_contradiction`, `not_found`, and `infrastructure_failure` immediately require re-evaluation; when a safe in-scope alternative exists, execution may make at most two materially different recovery attempts before waiting. `capability_rejected` and `damage_control_denied` may use an authorized alternative but must not be bypassed. A terminal wait requires one typed reason (`operator_decision`, `access_or_credential`, `external_dependency`, `safety_boundary`, `objective_conflict`, or `recovery_exhausted`), bounded evidence, and the required operator action. The current 20-failure threshold is removed; independent ready tasks continue while one task waits. Cancellation, no-replay, approval, and live-incident behavior remain intact.
- R8: Extension-generated goal and workflow progress or terminal reports must name the actual command, file, service, or target; the observed result; its effect on the objective; whether work continues; and the next action. The runtime cannot enforce wording for arbitrary model or external-tool output, but its prompts and generated reports must not substitute internal state labels or generic technical summaries for concrete facts.
- R9: Completion uses one recoverable closeout sequence: finish required plan and durable tasks; verify observed validation and artifacts; mark the canonical plan complete; archive its directory and persist the archived path while the goal remains active; include the archive in an identifiable in-scope commit; then verify that final HEAD contains the artifacts and that the worktree is clean. Only after those checks may the goal record completion and clear active state. An interrupted closeout reconciles the source and archive paths and resumes from an `archived_pending_commit` state without repeating completed work.
- R10: Cache work must not manually inject `cache_control` or `cachePoint`, couple child sessions to one session ID, change the root-Fable/subscription-leaf architecture, rewrite provider payloads outside a supported extension API, modify installed runtime code, add telemetry already represented by `cacheRead` and `cacheWrite`, or weaken Fable control-plane or security restrictions.
- R11: The cache assessment must confirm effective behavior for `amazon-bedrock/us.anthropic.claude-fable-5`, `bedrock-mantle/anthropic.claude-fable-5`, and OpenAI Codex child models. It must compare otherwise equivalent children for variation in system prompts, tool ordering, agent discovery, cwd context, and generated instructions. Existing usage records must be used to calculate provider/model cache-read and cache-write ratios when the current analytics entrypoint works; if it still fails because `pytz` is missing, record that limitation without repairing or replacing the analytics stack.
- R12: Any cache implementation requires evidence of a local defect, a structurally safe extension point, and an expected reuse benefit greater than the long-retention write premium. If `prompt_cache_key` cannot be set independently from session ID through the current Pi extension API, document the upstream limitation and make no local change. The terminal report must state whether code changed, the measured or structurally proven cache behavior, expected Bedrock dollar impact versus subscription-model impact, the upstream limitation, changed files, and validation results.
