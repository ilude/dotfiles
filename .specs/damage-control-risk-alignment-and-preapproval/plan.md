# Risk-based Damage Control, script preapproval, and failed-call protection

## Goal and scope

Make default Pi Damage Control prevent meaningful unrecoverable harm without treating routine recoverable work or suspicious-looking syntax as inherently dangerous. Implement the operator's broader scope: align all policy families identified by the completed risk review, improve contextual command decisions, add `/dc scan` and single-script preapproval, and retain a narrow unattended failed-call watchdog.

**User requirements:**

- Actual consequences govern. No inherited rule is exempt from reconsideration merely because it existed in legacy. Routine recoverable maintenance should run quietly; credible loss of meaningful data, uncommitted work, recovery mechanisms, important system state, sensitive information, or substantial irreversible resources warrants intervention.
- Use deterministic decisions for established routine cases and Luna judgment for consequential contextual cases. Neither unfamiliar syntax nor missing parser information alone establishes danger. Independent user/project authorization, including push/deployment restrictions, still applies.
- `/dc scan` reviews project-owned scripts using parallel subagents, without executing them. Repeated scans avoid re-reviewing unchanged completed results. Matching preapproved invocations skip script-body analysis; everything not covered falls back to normal runtime analysis.
- Store approvals in the repository's common Git directory, shared by all worktrees. Only outside Git, use the current project/location's `.pi/` directory. Preapproval can cover a script generally or a particular argument form when arguments materially change danger.
- Add `Allow once and review for future use` alongside `Allow once` and `Deny`. Run the permitted call without waiting for review; a qualifying review creates future approval without a second confirmation.
- Keep an unattended watchdog for repeated exact failed tool calls. Successful repetition is not a trigger. The operator proposed a tolerance around 12 failures, motivated by a reported June 2026 loop consuming roughly half a weekly Codex allowance; that incident was not independently verified during planning.

**Non-goals:** legacy changes; a new shell/parser framework, OS sandbox, universal harmlessness proof, package/dependency manager, mandatory project scans or environment inventories, broad self-integrity system, repeated security audits, fuzzy loop detection, durable job service, new production telemetry, extra approval wizard, or changes to Onclave/infrastructure. Do not add rollback work. Reuse the forthcoming default subagent runtime, not its own launcher or broker.

**Authorization:** planning only. Do not execute this plan until assigned. Execution then includes local task commits, archival and merge to recorded `main`, unless restricted; push and deployment remain separate. The completed risk review is input, not another audit to repeat.

### 2. Script identity, storage and runtime matching

Proposed implementation uses small typed records in YAML, indexed in memory. A record identifies a repository-relative script, its byte-content SHA-256, review outcome/reason, and either whole-script approval or exact approved argv. Add cwd or environment equality conditions only when review identifies their material effect on risk; no condition language, executable predicates or broad regex grants. Completed nonqualifying review results may be retained by hash to avoid redundant `/dc scan` model calls, but never bypass runtime analysis.

- Discover the repository from the operation's cwd, not the profile installation directory. Resolve the common Git directory using Git metadata; linked worktrees share `<git-common-dir>/pi/damage-control-trust.yaml`. Submodules remain separate repositories. Outside Git, use `<ctx.cwd>/.pi/damage-control-trust.yaml`; do not invent an ancestor project-detection service.
- Scan/match the actual worktree's file against the shared record. On a hash/condition miss, missing record, or unreadable/malformed store, use ordinary analysis, not a new approval requirement or global failure. Never auto-update a hash to preserve approval.
- Runtime still reads/hashes covered bytes; it skips body parsing/effect extraction and model review. Cache the YAML index and notice other instances' writes. Use the existing file-lock dependency plus atomic read-modify-write for shared updates. No database, background file crawler or hashing daemon.
- Protect the approval file as operator-authorized configuration using the existing narrow confirmation mechanism. Damage Control writes results of explicitly commissioned reviews; neither script text nor a reviewer's ordinary file-write tool can self-authorize an entry. Do not expand this into protecting all implementation files or a new trust wizard.
- Keep helpers proportional: proposed mechanism is a flat set of additional file hashes only where the reviewed invocation's consequential behavior depends on local helpers or a command definition. A changed required input invalidates that record. No dependency resolver, bundler, lockfile for installed packages, or automatic rejection solely because helpers exist. Unresolved helpers matter when they prevent a credible low-risk conclusion. Document ambient interpreter/package/startup assumptions rather than claiming an immutable execution environment.
- For an invocation that matches preapproval, skip that body, including its internal pattern checks. Do not claim internal hard blocks are reevaluated without parsing. Outer script invocation arguments, redirections, substitutions and additional commands still have their normal effect/authority checks. Keep source provenance so one script's grant cannot erase an adjacent command's findings.

### 3. Review and operator flow

Use one Damage Control review function for both entry points, adapted to the delivered subagent runtime. Its input identifies the script snapshot, invocation/conditions, originating repository/worktree/session, and relevant risk context. Its result is preapprove-with-reason/conditions, retain-runtime-analysis-with-reason, or failed/cancelled. Only a completed qualifying review can create approval, and only for the bytes actually reviewed. Source changes during review leave the new version unapproved.

`/dc scan` inventories project-owned scripts, excludes ignored dependencies/generated output, and partitions work among a small set of parallel read-only reviewers. Use current tracked and nonignored files for Git projects; ordinary bounded traversal for non-Git directories. Include existing supported script languages and extensionless shebang scripts. Package command definitions participate when they are a concrete entrypoint/helper, not through analysis of the complete dependency ecosystem. No arbitrary file-count completion requirement, automatic recurring scan, review consensus, or separate task registry.

Reviewers examine effects and recoverability, not a universal checklist. They never execute submitted scripts or gain shell/write/delegation tools merely to review. Use the new runtime's existing role/permission/surface/lifecycle behavior. The coordinator validates results and writes approved records; progress and completion remain concise, with script-specific reasons available when not approved. Valid completed results may be saved if another batch fails or is cancelled. Reuse the runtime's cancellation/inspection instead of adding a new job dashboard.

The prompt option is offered for an identifiable local script, not for arbitrary direct `rm` patterns. Preserve `Allow once` as the initial selection, Details, Escape-deny, RPC and no-UI behavior. Selecting review approves the whole pending call once, but future approval covers only the reviewed invocation. Dispatch asynchronously without waiting for review or scheduling a future prompt. If review is unavailable/fails, the current permission remains Allow once and future calls use normal analysis. No automatic model fallback or retry loop. Capture the originating context so later completion cannot write into a newly active project's store or notify the wrong chat.

### 4. Failed-call watchdog

The following is the recommended concrete contract, with one operator choice still open:

- Key: tool name + stable arguments + effective cwd. Preserve command text; do not use fuzzy similarity. Track Pi-reported failures (`isError`/thrown execution failures), including changed error output for the same call. Do not infer failure from words in successful output.
- Observe all model-callable tool events, including tools without a Damage Control policy adapter, without inventing policy adapters for them. Count each call ID once. Native shell nonzero exit/timeout uses the tool's real failure signal; verify this through the actual hook path.
- Threshold: allow at most 12 failed attempts, then refuse the next equivalent attempt and halt the affected agent run with the tool, command/input summary, cwd and count. No unattended confirmation loop or automatic resume. Do not terminate unrelated servers or Pi instances. Apply in child instances through their normal Damage Control loading; report failure to their owner through the existing runtime rather than adding cross-process counters.
- No limits on repeated successes. The same call succeeding clears its failure streak. Counts are session-owned, not persistent global history; ordinary assistant turns or compaction must not reset an ongoing loop. A tripped run stays stopped until a new direct operator instruction resumes it; queued automatic follow-ups must not immediately undo the stop. Verify reload/session lifecycle using the installed API, without a durable watchdog service.
- **D1, resolved by operator:** Unrelated calls reset the streak. Only adjacent exact failures count; the same signature also resets on success or direct operator resumption.
