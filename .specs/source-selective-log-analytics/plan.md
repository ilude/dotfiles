# Restore flexible Pi session and log analytics

## Objective

Replace the persistent projection pipeline with one invocation-local `@duckdb/node-api` engine that lets models query complete Pi session and log records using documented DuckDB SQL, returns incrementally bounded results, and supplies the same engine to extension, skill, orchestration, and failed-tool statistics without persistent analytics intermediates.

## Completion Evidence

- Evidence: Representative queries through the specified `withAnalyticsSession` interface find a known session by date and arbitrary content, identify its stable source and record keys, find known failed tool calls, and reproduce extension, skill, and orchestration fixture reports; selected same-named source views expose each complete original JSON record; DuckDB receives documented SQL without a competing Pi SQL grammar; simultaneous sessions remain independent; result iteration stops at row/byte bounds; and no analytics DuckDB/WAL file, projection table, staging JSONL, fingerprint, offset, global refresh, shared store, or full-corpus JavaScript aggregation remains.
- Fails when: Session or log fields are discarded, valid DuckDB SQL is rejected before DuckDB handles it, a match cannot identify its source session and record, unrelated sources are opened, one invocation closes or interrupts another, results are fully accumulated before output limits apply, an affected report changes behavior, or any superseded persistent analytics path remains.

## Boundaries

- In scope: The generic analytics engine and tool; session-backed extension and skill statistics; orchestration statistics and its staging path; failed-tool scanning and exported analytics readers; focused tests; `pi/README.md`; and the owning observability contract.
- Out of scope: `usage_report`, `/usage-stats`, provider `/usage`, append-only workflow-friction production, tool-failure decisions JSONL, bounded transcript inspection, damage-control or permission enforcement, live background-terminal state, correlation emitters, Arrow, worker pools, schedulers, retries, persistent snapshots, incremental caches, and the removed Python environment.
- Preserve: Canonical Pi JSONL as authority; full explicitly selected session and log content; configured Pi data-root and link-escape controls; disabled DuckDB external access outside prepared Pi views; bounded execution and returned output; cancellation; existing operator-facing report behavior; domain-owned decisions and enforcement; and unrelated working-tree changes.
- Assumptions: The public request is `{ operation: "query", sources: AnalyticsSourceId[], sql: string, parameters?: Record<string, string | number | boolean | null>, maxRows?: number }`; `catalog` returns stable source IDs, same-named view names, columns, and concise query hints. The internal boundary is `withAnalyticsSession({ root, sources, signal }, async session => session.query({ sql, parameters, maxRows, maxBytes }))`. It creates one in-memory DuckDB instance, uses a setup connection to create regular instance-local views for selected registered sources, then gives each `session.query` its own connection so cancellation, truncation, and closure cannot poison another query; the callback wrapper closes every query connection and finally the instance. Registered source definitions own canonical discovery and `CREATE VIEW` SQL, including domain sources now represented by custom `SourceDefinition`s; callers select IDs and do not supply files or definitions. `session.query` accepts named scalar parameters and returns `{ columns, rows, truncated }` using DuckDB's JSON row conversion, so `BIGINT` and other non-JavaScript values use DuckDB's JSON-safe representation and `NULL` remains `null`. `truncated` only reports that the returned row/byte bound stopped iteration and is not a coverage lifecycle. Date and content predicates are ordinary SQL. Content views expose `_source_file`, `_record_key` derived from the record ID or raw-JSON hash, `_timestamp` when present, and the complete original `record` as DuckDB JSON; additional typed columns are optional conveniences. `/do-it` must create and own the implementation worktree before changing files, then archive, commit, merge with `--no-ff`, verify merged HEAD, and remove only its owned worktree and branch.
