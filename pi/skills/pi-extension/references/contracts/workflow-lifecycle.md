# Interactive Workflow Lifecycle

- Dispatch feedback: `/plan-it` and `/do-it` render their submitted slash command immediately, before repository discovery, plan preflight, worktree setup, lifecycle persistence, or model dispatch can delay visible feedback. `/do-it` also shows the selected execution path, workspace, branch, execution mode, and effective closeout policy when dispatching; preparation alone does not mean execution started. Empty `/do-it` asks for the task without creating ownership or clearing the session.
- Ownership: `/plan-it` writes only the canonical plan in the primary repository and creates no branch or worktree. `/do-it` and `/goal` own deterministic Git worktrees beneath repository-root `.worktrees/`; their ownership records are durable, include the canonical `planPath` for new planned workflows, and implementation mutations are confined to those worktrees. Records without `planPath` remain readable for v1 restoration and acquire it when resumed with a canonical plan. Canonical `/do-it` accepts an optional leading `@` followed by `.specs/{slug}/plan.md` and bounded trailing punctuation, then selects and validates the primary input or owned resume plan before ownership is created or resumed; prose containing a plan path remains raw work. It may create its worktree while the primary contains the source plan or unrelated changes, but unrelated dirt blocks final merge and preserves recovery. New raw `/do-it` and `/goal` work still require a clean primary worktree.
- Planning: `/plan-it` creates one canonical primary `.specs/{slug}/plan.md` with a meaningful outcome-derived slug. Standard mode uses 0-4 subject-matter reviews according to the plan's actual risks, applies supported correctness and feasibility findings, then records one final necessity/subtractive review focused only on overengineering, gold-plating, unnecessary abstraction, duplicate state, excessive validation, and churn. Review strategy and concern are optional telemetry, not transition prerequisites or exact-text independence gates. A blocked lifecycle resumes the same canonical draft after its decision is resolved; it cannot switch plan paths. It calls ready only after the final subtractive review, all supported findings are resolved, and deterministic plan validation passes. Ready is idempotent so a stale repeated transition does not reopen or fail a completed planning lifecycle. Operator-selected `/plan-it quick [request]` is for small work sets and skips both review phases while retaining the same canonical plan contract and deterministic readiness validation. Git, worktree, transfer, commit, and anticipated merge state are `/do-it` execution context and never `/plan-it` blockers.
- Plan contract: include objective, observable completion evidence, mutation boundaries, executable tasks, real dependencies, validation, retention/archive instructions, and current status. A task-level `Verify:` may start with `deterministic` or `live`; an untagged check remains deterministic for compatibility. A live task also declares a positive `Max attempts`, an isolated `Session`, and `Terminal outcomes: supported | rejected | blocked`, and names one observable behavior plus cleanup without depending on a model choosing the action. Any plan with live work carries one `## Live attempt ledger` table with `Task | Attempt | Preconditions | Result | Cleanup | Disposition`. Each recorded row counts as an attempt; a Disposition beginning `Operator authorized` raises that task's effective cap by one, and reaching the effective cap requires an operator decision before `/do-it` starts the task. A `rejected` result completes a live evaluation task. Plans whose `Files:` span the workspace and one or more submodule or external repositories must name every repository, owner branch, and closeout in a Boundaries `Repositories:` bullet. Merge-and-cleanup closeout is the default. An operator may instead select commit-and-retain closeout through the exact Retention policy marker; this archives and commits on the workflow branch without merging and preserves the owned worktree, branch, and ownership record. Do not invent scheduler state or duplicate ledgers.
- Execution input: `/do-it` accepts raw work or a canonical plan through direct interactive or RPC input; an execution verb plus an exact plan path, or uniquely identified `this plan`, may route to it, while extension input cannot. Only exact `--no-clear`, `--in-place`, and `--no-merge` flags select their named behaviors, `--` makes later text literal, and prose never implies a flag. Native completion presents valid active plans and applicable flags.
- Execution preflight: prepare the owned workspace and validate the actual execution plan before session clearing. Reject unsafe paths, non-regular files, unsupported status, invalid task graphs, and unsupported source states. Accepted plans may be clean tracked files, wholly new nonignored files, ignored files, or tracked `plan.md` files with only unstaged changes; ignored plans remain recoverable and are never force-added. Setup failure preserves the current session and recovery files, and immediately publishes the stage, exact paths or Git state, lack of dispatch, and next action to the transcript and model context without starting a model turn or waiting for another user prompt. After successful preparation, valid plans and raw work start in a fresh session unless `--no-clear` is present. When the footer's reload detector is active, `/clear` reloads resources through the fresh replacement-session context, and `/do-it` defers its continuation until that reload completes; neither command reloads when the detector is inactive, and `--no-clear` remains an immediate bypass. The continuation carries the prepared execution context, verifies ownership/branch, canonical plan path, effective closeout policy, and unchanged execution-plan bytes after replacement, and dispatches once through the fresh extension instance; it never silently selects a different plan or uses a superseded closeout decision. Cancelled session replacement reports that execution was not dispatched, identifies the preserved prepared workspace, and gives a retry action without removing prepared files.
- Execution ownership: work uses one durable owned worktree by default, while `--in-place` selects verified in-place execution. Resume preserves execution progress, follows the recorded execution mode without requiring `--in-place` again, rejects a conflicting mode, and starts at the first unchecked dependency-ready task. An existing worktree alone does not establish successful setup: a clean worktree still at its initial baseline may receive the primary plan's supported unstaged edits. Divergent primary edits and owned changes or commits require reconciliation without overwriting either copy. When the primary spec is unchanged from setup or absent after transfer, resume the owned plan rather than revalidating an obsolete primary copy. Git and the plan remain the recovery authorities; there is no additional execution ledger. Live tasks stop for an operator decision when their effective attempt cap is exhausted.
- Execution closeout: default closeout archives and commits the completed plan, merges the owned branch with `--no-ff`, verifies the archive, merge, ownership, and clean states, then removes only the owned branch and worktree. `--no-merge` selects commit-and-retain and overrides a plan's default; with `--in-place` it is redundant and cannot weaken verification. Retained closeout verifies the committed unmerged branch and preserves its worktree and ownership record. Any validation, archive, commit, merge, conflict, or cleanup failure preserves recovery state rather than replaying work. Retrying the original canonical `/do-it` command after archival recognizes the completed archive in its owned workspace before considering an older primary copy. It resumes closeout only, keeps the original plan path for verification, and never recreates the active plan or reruns implementation. The archive bytes remain bound to the prepared handoff.
- Execution review: execution adds no review after readiness; validation uses the closed contract. Deterministic plan validation checks machine-consumed state, not prose quality: no literal cleanup keyword, conjunction count, model-choice wording rule, arbitrary task-count cap, or template-heading/field checks beyond the parser's required structure. Objective, evidence, boundaries, verification design, cleanup adequacy, and cross-repository ownership remain contextual planning/review obligations. Readiness checks declared live metadata; execution checks live metadata and the ledger when the next dependency-ready task is live. Missing prerequisites for later live work do not prevent earlier implementation. Before any live action, the root verifies its actual target, authorization, attempt limit, stop condition, and cleanup; unsafe or unresolved actions remain blocked.
- Raw work: bounded direct work needs no plan or durable task. Create one root task only when raw work is likely to span compaction, delegation, or delayed continuation.
- Validation: run the smallest checks that directly exercise the completion evidence. A reported command, stale result, or model summary does not substitute for observed validation.
- Closeout: after all tasks and validation pass, the model performs archive and commit work in the owned workflow context. By default it also performs the `--no-ff` merge; under commit-and-retain policy it must not merge, must not force-add or commit plans ignored by the primary repository, and leaves the worktree, branch, and ownership record intact after deterministic verification. Closeout tool transcript rows show their local start time while running and their start time plus settled duration after completion. A deterministic verifier checks the exact archived plan, clean branch/worktree, primary cleanliness, and ownership. Default closeout additionally requires the merged HEAD before removing only the owned worktree and branch; retained closeout requires an unmerged committed workflow branch and preserves all owned resources. Successful `plan_archive` and `workflow_complete` results present concise dynamic summaries using the verified source plan, archive plan, workflow branch, and primary branch while retaining structured details for machine use. Closeout failures throw through Pi's tool-error protocol so the runtime records a failed tool execution, while preserving recoverable ownership and files. Never replay a partially observed archive, commit, or merge blindly. Tracked changes and untracked files outside canonical `.specs/{slug}/plan.md` block verification; another workflow's untracked canonical plan does not block merge or cleanup. Unmerged, conflict, failed-merge, or failed-cleanup states preserve ownership. Reject incomplete plans, unsafe paths, and collisions.
- Compatibility: legacy lifecycle stages may be read for restoration, but removed review/adjudication stages are not current workflow gates. The obsolete review-only command and artifact tool are not registered or discoverable.
