# Interactive Workflow Lifecycle

- Dispatch feedback: `/plan-it` and `/do-it` render their submitted slash command immediately, before repository discovery, plan preflight, worktree setup, lifecycle persistence, or model dispatch can delay visible feedback.
- Ownership: `/plan-it` writes only the canonical plan in the primary repository and creates no branch or worktree. `/do-it` and `/goal` own deterministic Git worktrees beneath repository-root `.worktrees/`; their ownership records are durable, include the canonical `planPath` for new planned workflows, and implementation mutations are confined to those worktrees. Records without `planPath` remain readable for v1 restoration and acquire it when resumed with a canonical plan. Canonical `/do-it` accepts an optional leading `@` followed by `.specs/{slug}/plan.md` and bounded trailing punctuation, then validates the primary plan before ownership is created or resumed; prose containing a plan path remains raw work. It may create its worktree while the primary contains the source plan or unrelated changes, but unrelated dirt blocks final merge and preserves recovery. New raw `/do-it` and `/goal` work still require a clean primary worktree.
- Planning: `/plan-it` creates one canonical primary `.specs/{slug}/plan.md` with a meaningful outcome-derived slug. Standard mode uses 0-4 subject-matter reviews according to the plan's actual risks, applies supported correctness and feasibility findings, then records one final necessity/subtractive review focused only on overengineering, gold-plating, unnecessary abstraction, duplicate state, excessive validation, and churn. Review strategy and concern are optional telemetry, not transition prerequisites or exact-text independence gates. A blocked lifecycle resumes the same canonical draft after its decision is resolved; it cannot switch plan paths. It calls ready only after the final subtractive review, all supported findings are resolved, and deterministic plan validation passes. Ready is idempotent so a stale repeated transition does not reopen or fail a completed planning lifecycle. Operator-selected `/plan-it quick [request]` is for small work sets and skips both review phases while retaining the same canonical plan contract and deterministic readiness validation. Git, worktree, transfer, commit, and anticipated merge state are `/do-it` execution context and never `/plan-it` blockers.
- Plan contract: include objective, observable completion evidence, mutation boundaries, executable tasks, real dependencies, validation, retention/archive instructions, and current status. A task-level `Verify:` may start with `deterministic` or `live`; an untagged check remains deterministic for compatibility. A live task also declares a positive `Max attempts`, an isolated `Session`, and `Terminal outcomes: supported | rejected | blocked`, and names one observable behavior plus cleanup without depending on a model choosing the action. Any plan with live work carries one `## Live attempt ledger` table with `Task | Attempt | Preconditions | Result | Cleanup | Disposition`. Each recorded row counts as an attempt; a Disposition beginning `Operator authorized` raises that task's effective cap by one, and reaching the effective cap requires an operator decision before `/do-it` starts the task. A `rejected` result completes a live evaluation task. Plans whose `Files:` span the workspace and one or more submodule or external repositories must name every repository, owner branch, and closeout in a Boundaries `Repositories:` bullet. Merge-and-cleanup closeout is the default. An operator may instead select commit-and-retain closeout through the exact Retention policy marker; this archives and commits on the workflow branch without merging and preserves the owned worktree, branch, and ownership record. Do not invent scheduler state or duplicate ledgers.
- Execution: `/do-it` validates a canonical plan before clearing, so a failed preflight preserves the current session; valid canonical plans and raw work clear into one fresh session and use an owned worktree by default. That new-session replacement is the sole extension refresh; `/do-it` does not follow it with a redundant reload. Before dispatching the next dependency-ready live task, it counts that task's ledger rows against its effective cap and stops with a task-specific operator decision when no attempt remains. Only exact `--no-clear`, `--in-place`, and `--no-merge` flags select their named behavior; `--` makes following text literal, and plan or commit wording never implies any flag. `--no-merge` selects commit-and-retain closeout and overrides a canonical plan's default merge policy; with `--in-place` it is redundant and must not weaken in-place verification. A cleared continuation carries one private ID and its parsed options into the replacement session, where a durable transcript acknowledgement appears without emitting a synthetic public `/do-it` message. The fresh extension instance launches through one internal path and records that ID as consumed only after execution or recovery dispatch succeeds, or after a terminal operator stop is reported; setup, validation, and unexpected dispatch failures remain pending for reload recovery. On resume, explicit flags are authoritative: `--no-clear` controls only conversation clearing, while worktree and file state always survive; explicit `--no-merge` upgrades closeout to retain, and omitting it preserves the existing ownership or plan policy. Active ownership determines the execution mode on resume: in-place ownership resumes without requiring `--in-place`, while ordinary-worktree ownership rejects an explicit `--in-place` before mutation or model dispatch. Execution strategy is optional advisory prose and is not machine-validated. Plan readiness checks authoring quality, while `/do-it` execution preflight checks only machine-consumed state: canonical path and regular file containment, executable tasks and dependency integrity, and a supported persisted status. Argument completion is native and cached, refreshed on session transitions, plan readiness, and successful archival; it includes only valid active canonical plans and remaining exact flags. Direct execution routing accepts only bounded interactive or RPC input for an execution verb plus an exact canonical path, or uniquely identified `this plan`; extension input cannot mint the route. When `/do-it` receives a canonical plan, it validates the primary plan before creating its worktree, then materializes the spec there as the sole execution ledger. An entirely untracked nonignored spec transfers into the worktree; an ignored spec is copied while its primary source remains recoverable and is never force-added; clean tracked plans already exist in the worktree; an unstaged modification of the tracked canonical `plan.md` transfers into the worktree and the primary copy returns to its committed content after verification. Staged, mixed, renamed, deleted, or supporting-spec tracked changes reject without alteration. Resume from the first unchecked dependency-ready task and update it after each verified result. Do not mirror its checklist into durable tasks unless separately requested. Raw `/do-it` is valid only after ownership is established. Raw `--no-merge` closeout commits and retains the owned workflow branch, worktree, and ownership record through the retained-worktree verifier. Canonical persisted plan status controls routing: a completed active plan is reported as already complete, does not rerun implementation or validation, and receives bounded recovery context for inspection and closeout only.
- Raw work: bounded direct work needs no plan or durable task. Create one root task only when raw work is likely to span compaction, delegation, or delayed continuation.
- Validation: run the smallest checks that directly exercise the completion evidence. A reported command, stale result, or model summary does not substitute for observed validation.
- Closeout: after all tasks and validation pass, the model performs archive and commit work in the owned workflow context. By default it also performs the `--no-ff` merge; under commit-and-retain policy it must not merge, must not force-add or commit plans ignored by the primary repository, and leaves the worktree, branch, and ownership record intact after deterministic verification. Closeout tool transcript rows show their local start time while running and their start time plus settled duration after completion. A deterministic verifier checks the exact archived plan, clean branch/worktree, primary cleanliness, and ownership. Default closeout additionally requires the merged HEAD before removing only the owned worktree and branch; retained closeout requires an unmerged committed workflow branch and preserves all owned resources. Successful `plan_archive` and `workflow_complete` results present concise dynamic summaries using the verified source plan, archive plan, workflow branch, and primary branch while retaining structured details for machine use. Closeout failures preserve the recovery worktree; never replay a partially observed archive, commit, or merge blindly. Tracked changes and untracked files outside canonical `.specs/{slug}/plan.md` block verification; another workflow's untracked canonical plan does not block merge or cleanup. Unmerged, conflict, failed-merge, or failed-cleanup states preserve ownership. Reject incomplete plans, unsafe paths, and collisions.
- Compatibility: legacy lifecycle stages may be read for restoration, but removed review/adjudication stages are not current workflow gates. The obsolete review-only command and artifact tool are not registered or discoverable.
