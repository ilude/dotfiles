# Interactive Workflow Lifecycle

- Dispatch feedback: `/plan-it` and `/do-it` render their submitted slash command immediately, before repository discovery, plan preflight, worktree setup, lifecycle persistence, or model dispatch can delay visible feedback.
- Ownership: `/plan-it` writes only the canonical plan in the primary repository and creates no branch or worktree. `/do-it` and `/goal` own deterministic Git worktrees beneath repository-root `.worktrees/`; their ownership records are durable and implementation mutations are confined to those worktrees. Canonical `/do-it` may create its worktree while the primary contains the source plan or unrelated changes, but unrelated dirt blocks final merge and preserves recovery. New raw `/do-it` and `/goal` work still require a clean primary worktree.
- Planning: `/plan-it` creates one canonical primary `.specs/{slug}/plan.md` with a meaningful outcome-derived slug. After drafting, delegate adversarial review to 2-4 independent subject-matter experts selected for the plan's actual domains, apply supported correctness and feasibility findings, then delegate one fresh final review focused only on overengineering, gold-plating, unnecessary abstraction, duplicate state, excessive validation, and churn. Apply necessary subtractive findings and call ready only after at least two subject-matter reviews, the final subtractive review, and deterministic plan validation pass. Git, worktree, transfer, commit, and anticipated merge state are `/do-it` execution context and never `/plan-it` blockers.
- Plan contract: include objective, observable completion evidence, mutation boundaries, executable tasks, real dependencies, validation, retention/archive instructions, and current status. Do not invent scheduler state or duplicate ledgers.
- Execution: when `/do-it` receives a canonical plan, it validates the primary plan before creating its worktree, then materializes the spec there as the sole execution ledger. An entirely untracked nonignored spec transfers into the worktree; an ignored spec is copied while its primary source remains recoverable and is never force-added; clean tracked plans already exist in the worktree; an unstaged modification of the tracked canonical `plan.md` transfers into the worktree and the primary copy returns to its committed content after verification. Staged, mixed, renamed, deleted, or supporting-spec tracked changes reject without alteration. Resume from the first unchecked dependency-ready task and update it after each verified result. Do not mirror its checklist into durable tasks unless separately requested. Raw `/do-it` is valid only after ownership is established.
- Raw work: bounded direct work needs no plan or durable task. Create one root task only when raw work is likely to span compaction, delegation, or delayed continuation.
- Validation: run the smallest checks that directly exercise the completion evidence. A reported command, stale result, or model summary does not substitute for observed validation.
- Closeout: after all tasks and validation pass, archive the entire spec directory in the implementation worktree, commit nonignored artifacts, merge with `--no-ff` into the primary worktree branch, verify merged HEAD, mark ownership complete, and remove only the owned worktree and branch. For an ignored spec, copy the completed archive back to the primary local ignored archive without force-adding it, and remove the original local source only after merge succeeds. A dirty primary blocks closeout; unmerged, conflict, failed-merge, or failed-cleanup states preserve the recovery worktree. Reject incomplete plans, unsafe paths, and collisions.
- Compatibility: legacy lifecycle stages may be read for restoration, but removed review/adjudication stages are not current workflow gates. The obsolete review-only command and artifact tool are not registered or discoverable.
