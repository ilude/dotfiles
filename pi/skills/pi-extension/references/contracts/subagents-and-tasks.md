# Subagents and Durable Tasks

## Tree execution

- The selected primary model owns root orchestration. Current calls select `subagent_read`, `subagent_write`, or `subagent_teamlead`; role inference remains only in the hidden historical adapter. A Team Lead may run subagents only; subagents and depth-two children cannot invoke delegation or workflow tools.
- The root-owned cross-process tree scheduler queues descendants and enforces eight active descendants by default. `PI_SUBAGENT_MAX_ACTIVE_DESCENDANTS` may configure a ceiling from 1 through 16. Authenticated broker frames are size-bounded; client requests handle abort, premature close, and stalled transport without releasing capacity before broker settlement.
- Every child role shares a 64-turn ceiling, including structured-output correction. Team Lead requests also carry bounded subagent, turn, and soft-deadline budgets and return explicit partial results when a budget settles the process.
- Cancelling a Team Lead process or workflow recursively cancels queued and active descendant processes. A child capability may cancel only itself and its descendants; it cannot cancel or release an ancestor or sibling. Cancellation, process settlement, and permit release are idempotent.
- One failed or skipped subagent is represented as that subagent's result and does not cancel an unrelated subagent unless the invocation-level signal is aborted.
- `/subagents` can cancel a selected process-local tree. Run snapshots, bounded transcripts, live output, workflow state, and settled workflow results are process-local. They survive `/reload`, `/new`, `/resume`, and `/fork` in the same process and are discarded at process exit. Preserve full child output through an explicit child session or artifact when durable evidence is required.
- Footer visibility is actionable rather than historical: show running and unacknowledged failed counts, omit completed and cancelled counts, clear successful settlement immediately, and acknowledge existing failures when the next interactive user turn starts. A failure that occurs after that turn starts remains visible. Render failure status with the error theme and keep `/subagents` as the detailed history surface.

## Callable subagent behavior

- `subagent_read` runs one or more read subagents with a closed positive tool allowlist and no raw `bash` or `pwsh`. `subagent_write` runs modifying subagents. `subagent_teamlead` runs bounded Team Leads. All accept `instructions`, `boundaryPaths`, `boundary`, and an `enforcedBoundary`; only a root may widen execution beyond its inherited boundary. Each item may add validated skills by name; dispatch-selected skills are merged with the registered agent profile's skills and do not change tool authority.
- `boundaryPaths` and `boundary` are advisory markers shown in status and telemetry. Overlap is reported but never rejects or queues a subagent.
- Governed native file tools and recognized recursive `rg`, `grep`, and `find` targets must remain inside the effective boundary. A read-class child may additionally read only the exact canonical selected-skill files supplied for that invocation; their parent directories, neighboring files, search traversal, shell access, and mutation remain outside that exception. Static `cd` targets are checked; dynamic or filesystem-root recursive targets reject. Path-escape errors identify the assigned workspace, supplied path, and resolved path that failed containment. This governs known tool activity, not arbitrary programs launched by shell commands, and is not a general sandbox.
- `subagent_status` is root-only and accepts either an exact process ID or the orchestration ID returned by background start; model calls must name a target, while `/subagents` is the listing surface. Exact-process status reports PID, liveness, latest observable activity, activity version, active tools, tool duration, output age, usage, and a ping-backed classification: `responsive-quiet`, `stalled-tool`, `unresponsive-runtime`, or `dead-process`. Models must never use status to poll work progress. An unchanged target/status/activity observation is blocked and aborts the current model run once; real activity or a terminal-status change permits a later diagnosis. They wait for pushed completion, timeout, or watchdog events and use status only for exceptional diagnosis after one of those signals or other direct evidence.
- `subagent_control` targets an exact authorized run or tree. Interrupting a stalled tool terminates and settles that child process tree, then resumes the persisted child session with a recovery message. Recovery rejection identifies the requested run and tool IDs and reports only bounded active-tool context from that selected authorized run. The interrupted tool result, side effects, and unpersisted output remain unknown and must be rechecked.
- Subagent transcript rows show `started HH:MM:SS local` while represented work is running and `started HH:MM:SS local | duration <value>` after settlement. Detached acknowledgements and completions use the run manager's authoritative run start timestamp; this does not alter model-facing result content, status, footer, or dashboard output. `subagent_control` uses timing only for `interrupt_tool`; immediate control actions remain untimed.
- `subagent` and `subagent_continue` remain hidden compatibility tools for historical resumed sessions. New calls use the role-specific interfaces.
- Validate every requested agent against the current trust-aware catalog and `agentScope` before starting any subagent or acknowledging background work. A rejected selection reports the rejected names, active scope, and sorted usable alternatives from that effective catalog. Trusted project-agent names enter the callable schema only after trust validation; cwd or trust changes rebuild the catalog rather than falling back to untrusted project discovery. Project agents require `agentScope: "project"` or `"both"`; unknown names do not resolve as aliases. When `confirmProjectAgents` is requested, reject before spawn if no UI is available rather than bypassing confirmation.
- An optional `taskId` requires an existing non-deleted assigned task in the effective workspace and provides correlation only. Task lookup rejection identifies the requested ID and current-workspace lookup context. Subagent calls never create or transition `TaskRecordV1` entries. Single-item modern calls may also provide `affinityTaskId`; the new run remains correlated to its current `taskId`, while child cache telemetry carries `runId`, `taskId`, `continuationStatus`, and a per-run provider-request ordinal. A missing child `runId` identifies a root request. Cache joins use unique `runId` only.
- Modern `subagent_read` and `subagent_write` single-item calls may explicitly provide `affinityTaskId` as a prior task ID. The current item must also provide `taskId`; that task remains the correlation for the new run. Affinity is rejected for multi-item and Team Lead calls before spawn. Resolution scans process-local settled runs and requires a saved session, exact root-session and canonical-workspace identities, OpenAI Codex Luna model and effort, immutable profile/skills/role/depth/authority fingerprint, and a unique latest settlement. Affinity rejection identifies `affinityTaskId`, a bounded eligible-candidate count, and a non-sensitive eligibility reason. A canonical saved-session lease is acquired atomically before spawn and held through settlement and session persistence; no automatic routing or durable affinity registry is added.
- Versioned model and topology recommendations are advisory. Selection mismatches remain executable and are recorded with the selected route and outcome. Luna low is preferred for tool-heavy inspection, exploration, validation, and summarization; Sol low or Luna high for bounded planning; Sol low for Team Leads and subagent team managers; Luna medium or high for implementation; and Sol low for review. Max effort requires per-invocation operator approval or the explicit `PI_SUBAGENT_ALLOW_MAX=1` operator policy.
- Claude Fable and Opus roots on `amazon-bedrock` or `bedrock-mantle` cannot start a Team Lead or continue a saved child session. Single and parallel subagent requests are preflighted after trusted agent discovery. Explicit models and agent pins must resolve to an available `openai-codex` model; omitted and size-based requests select only from available `openai-codex` models. Size-based requests use Luna for `small` and `medium`, and Sol low for `large`. One invalid request rejects the complete invocation before any child starts.
- Provider-visible output selection can enable or disable runtime-generated private artifacts but cannot name an arbitrary path. Legacy string paths remain executable only for resumed or direct compatibility calls. Single, parallel, and background subagent results at or above 16 KiB are bounded to 16 KiB with complete output saved to a runtime-generated private artifact and an artifact reference; smaller output and explicit `file-only` results remain unchanged. If artifact saving fails, retain the existing 50 KB or 2000-line fallback with an explicit error. Internal handoff keeps complete output or an artifact reference. Restricted Bedrock Claude roots retain the same boundary and cannot select a custom output path.

## Workspace and durable-task boundaries

- The effective workspace is canonicalized before trust, agent, and task-link validation. Existing symlinks and the nearest existing ancestor of a prospective target are resolved before containment is accepted.
- Read leaves use only the closed read authority. Write leaves retain their configured mutation tools, but governed file and recognized recursive-search targets cannot escape the effective workspace. Advisory work markers do not grant authority and need not be disjoint. Rejections identify the parent workspace, supplied workspace, and resolved workspace or target when available; scope rejections identify the repository root, supplied scope, and resolved target. These diagnostics do not weaken containment or disclose unrelated filesystem state.
- The root-only Onclave capability is removed from every direct and broker child environment. An inherited ineligibility marker prevents a nested Pi from initializing or reserving an Onclave connection even if ordinary subagent markers are removed.
- Only `task` creates durable todo records. The root selects ready work, assigns it, delegates with the existing `taskId`, validates the result, and records terminal state. Modern per-item links and legacy links use one pre-spawn validator for effective workspace, root session, non-deleted existence, and assigned state. Legacy top-level `taskId` is normalized once only for a single item. One direct subagent or Team Lead may carry that task ID for correlation; children and retries never mutate task state. Current completed transitions require a bounded root-owned terminal outcome with nonblank summary and evidence; optional validation is limited to Task Instructions and gaps may be recorded. Bound violations identify the field, actual count or length, maximum, and offending index without rendering item contents. Invalid transitions identify the task ID, current state, attempted state, and allowed states. Dependency-cycle rejection identifies only cycle members in the validated workspace graph. Legacy terminal records without an outcome remain readable, and retry clears the current terminal outcome.
- Before each process starts, the task extension surfaces assigned root tasks owned by the current session and workspace. It lists up to eight IDs and summaries, reports any remainder, and never chooses among multiple candidates. Tasks from other sessions are never injected into model context. No reminder is added when none are assigned.
- After compaction or resume, the root task Instructions, boundaries, goal coverage, and acceptance checks remain authoritative. Add another task only for an independently verifiable deliverable required by those checks; when user correction changes the outcome, update the root task Instructions before continuing and skip work no longer required.
- Task and `/tasks` creation records the owning Pi session and workspace. Create requires a nonblank summary, batch requires 1 through 16 items, and create, update, and batch validate unique dependencies against non-tombstoned records in the same workspace while allowing legacy blockers without workspace metadata. Boundary metadata is bounded, slash-normalized, and retained as descriptive strings; absolute and parent-relative entries are valid, and boundary metadata does not enforce worktree containment or tool authority. `blockedBy` is the persisted dependency authority; reverse `blocks` views are derived when records are read. Default model-facing list and ready views show only that session and workspace; model-facing `all` includes retained records from the current workspace across sessions. Explicit operator `/tasks --all` views may include other workspaces and terminal records. Session startup pruning removes pre-session records that cannot be assigned safely.
- The run manager owns live process state. Its global reload record carries the explicit `dotfiles.pi.subagent-run-manager.v1` ABI marker. Reload reuses a shape-compatible manager, replaces an incompatible quiescent manager, and fails explicitly when incompatible live runs or pending completions are observable. The task registry owns durable todo and dependency state. Neither mutates the other's lifecycle.

## Unattended goal recovery

- `/goal --unattended` tracks attempts and recovery per linked durable root task across loop invocations. The task registry is authoritative for task requirements, dependencies, and outcomes; goal state stores task IDs plus goal-specific attempt, recovery, validation, artifact, blocker, and gap evidence rather than a second task graph.
- `error`, `inconclusive`, schema-invalid output, verifier contradiction, `not_found`, and infrastructure failure immediately suspend the affected ordinary attempt and require persisted re-evaluation. At most two materially different recovery attempts are allowed; two failures set only that item to a typed `recovery_exhausted` wait.
- Every terminal wait records one allowed reason, bounded evidence, and the required operator action. Capability rejection and damage-control denial may use an authorized alternative but are never bypassed. Cancellation and the repeated identical tool-result guard remain independent.
- `/goal --unattended` materializes one durable root task per canonical plan key with the parsed `Depends on` graph and task-level `Done when` and `Verify` checks before modification. Goal ID, objective hash, canonical plan path, and task key metadata make partial batches idempotently reconcilable; child-owned task records cannot satisfy the mapping. Ordinary foreground `/goal <objective>` remains direct and session-owned unless a reviewed plan is explicitly supplied or material risk or ambiguity requires one.
- Ask-tier damage-control decisions without UI return `needs_approval` with a redacted decision reference. The active linked root task becomes blocked while independent ready tasks may continue; the denied action is never replayed automatically.
