# Quality Gates

- Ownership: Pi runtime validation is configured by `pi/quality-gates.json` and implemented by `pi/extensions/quality-gates.ts`. Other clients may use independent policies; their behavior is not the Pi contract.
- Collection: track files changed successfully through supported mutation tools. Settlement records and clears the pending set but does not execute validators or fixes under the shipped policy.
- Selection: choose language and validators from configured extensions, project markers, scope, and detection rules. Every shipped command validator is explicit-only (`automatic: false`); Lizard is also not a settlement validator. Explicit callers may still select and run configured validators.
- Execution: explicit validation invokes validator commands without shell interpolation, bounds their output, and classifies pass, failure, unavailable, skipped, advisory, and duration mechanically.
- Paths: automatic collection excludes configured generated, dependency, vendor, build, and immutable paths, and omits removed or unchanged files. Explicit callers must apply the same exclusions; configuration is authoritative.
- Autofix: the low-level validator runner honors an explicit autofix option for configured fix commands; it does not itself check Git attributes. Explicit callers must honor `quality-autofix=off` before requesting mutation. Keep initial final-phase validation check-only, classify failures, then count any selected fix and recheck within the root's shared repair/rerun allowance. Do not hide additional repair cycles inside an explicit call.
- Settlement: under the shipped policy, settlement may record skipped-validator metadata but does not run validators, fixes, repair turns, or delegated model runs. Final development validation is an explicit workflow step after edits integrate. The existing `automatic` setting remains configurable; changing it opts into settlement checks, not completion-aware batching.
- Evidence reuse: explicit validation may reuse unchanged validation evidence and replay prior failures where supported. Do not treat duplicate output as a fresh check.
- Reporting: report observed blocking failures without fabricating success. Advisory findings remain nonblocking. Missing tools are unavailable evidence, not proof that the target passed.
