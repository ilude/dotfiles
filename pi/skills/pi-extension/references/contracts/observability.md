# Observability, Transcripts, and Usage

- Separation: content-bearing transcripts and metadata-only operational metrics are different trust boundaries. Never treat one as interchangeable with the other.
- Transcripts: tracing is off by default and enabled only in per-user runtime settings. It may capture provider payloads, visible assistant content and thinking, tool inputs/results, errors, and selected headers. Hidden provider reasoning is never captured.
- Transcript safety: clone and redact before persistence, restrict local permissions, reject configured cloud-sync paths, spill oversized redacted fields to bounded companion files, and correlate records without emitting per-token events.
- Transcript retention: apply configured retention at session start and support explicit purge. A bare `/transcript-purge` age is measured in days; explicit `ms`, `s`, `m`, `h`, and `d` suffixes remain supported. Purge only the inspected trace and spill boundary.
- Metrics: metrics are best-effort, append-only operational metadata. Producers must not include prompts, tool arguments, terminal output, response content, secrets, or unbounded free text.
- Failure: disabled or failed observability must not break the primary tool, workflow, or session operation. Record gaps rather than inventing missing evidence.
- Interpretation: metrics and traces are observational. They do not by themselves prove correctness, completion, quality, causality, or savings. Missing pricing is unknown cost, not zero cost.
- Tool-failure authority: `/find-fails` is a TypeScript-only bounded diagnostic. `pi/lib/tool-failure-classifier.ts`, `pi/lib/tool-failure-decisions.ts`, and `pi/lib/tool-failure-store.ts` own deterministic joins, fingerprints, timestamp windows, custom-extension filtering, thresholds, stable selection of at most three candidates, ledger precedence, and append-only decisions. The local DuckDB database is a disposable read model; session JSONL and the private decision JSONL remain authoritative evidence.
- Selection: post-effective regressions and changed fingerprints precede internal defects, recent multi-session failures, repeated workflow blockers, and sufficiently evidenced unclassified failures. Structural counts and model confidence never qualify a decision. Missing, malformed, future, stale, contradictory, or incomplete evidence remains unresolved.
- Decision safety: the narrow writer may append only an evidence-proven documented safety or authority rejection, accurate caller-contract rejection, deliberate cancellation, temporary external failure with a revisit date, or proven fix with typed evidence and an effective date. Reasons and evidence reject secrets, absolute private paths, control characters, and multiline content. Appends use a cooperating lock, write one complete sanitized record, flush and fsync before success, and ignore or quarantine only an incomplete trailing record without rewriting valid prior records.
- Provider and inspection boundary: a diagnostic run starts exactly one normal active-session turn, not an isolated model call or shortlist transcript message. It discloses the provider boundary, exposes only bounded selected-coordinate transcript inspection (`tool_failure_inspect`) and the narrow decision writer (`tool_failure_decide`), denies protected, generated, private, and out-of-workspace paths before reading, redacts before delivery, and enforces per-call and per-turn item and byte limits. The active model reads selected evidence itself. It cannot mutate repository files or delegate work. Agent end, cancellation, error, reload, and session transition settle the owned restriction by recomputing the desired tool set.
- Report boundary: every finding uses one human verdict from `Failing`, `Fixed`, `Expected`, `External`, or `Unresolved`, followed by `Last seen: M/D/YYYY h:mm:ss AM/PM` in local time and concise evidence. `Fixed`, `Expected`, and `External` require their direct proof. The report states once that no code changed and never exposes ledger terms or assumed future-scan behavior. It offers action only when action remains and does not invent options.
- Retention boundary: metrics currently have no built-in retention guarantee. Do not promise automatic deletion, permanent retention, or cross-machine synchronization without an explicit policy.
- Storage: generated sessions, histories, traces, metrics, workflow-friction records, caches, and indexes remain local runtime state and are not tracked repository source.
