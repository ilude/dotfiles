# Managed Background Terminals

- Classification: process-local shell execution for long-lived servers, watchers, and concurrent command work. It is not a durable task system and must not share the subagent run manager.
- Safety boundary: `bg_start` commands use Bash syntax on supported platforms and pass through the same damage-control shell analysis as `bash` before a process starts. Damage-control blocks and approvals must occur before manager registration or process spawning. Reject unwaited shell background operators from both tools: use `bg_start` instead of detached `bash`, and keep the managed command itself in the foreground because `bg_start` is already asynchronous.
- Execution authority: one bounded process-global `BackgroundTerminalManager` owns child-process lifecycle, output capture, and live state. Background terminals and subagents share only the cross-platform process-tree termination primitive and the narrow acknowledged-delivery adapter; they do not share managers, queues, or lifecycle state. The `/ps` dashboard is the interactive projection over background-terminal state; background terminals do not render a separate status widget because the footer owns process activity status.
- Visibility: register and keep `bg_start` and `bg_kill` active. Use `/ps` for operator inspection; the model does not receive separate status or list tools.
- Origin: `bg_start` captures the required parent session ID and canonicalized parent `ctx.cwd` before resolving the worker boundary or spawning. Completion routing requires both exact origin fields. A new, forked, or switched session never receives a foreign completion; resuming the original session and workspace may receive it. Legacy entries without a reliable origin are retained as explicitly blocked diagnostics and are never matched from worker cwd or an undefined session ID.
- Completion: a start returns immediately. Its acknowledgement includes the manager-authoritative start time. Natural completion delivers one bounded follow-up result through `sendMessageWithReceipt`, with the manager-authoritative start time and settled duration. The completion remains in the manager until an exact inserted receipt or existing explicit `bg_kill` consumption. Repeated scheduling hooks do not resubmit an in-flight receipt. An awaited `bg_kill` consumes that completion so the kill result and automatic follow-up do not duplicate each other; if an already-started receipt later inserts, the authoritative state records the ordering rather than claiming retroactive deduplication.
- Receipt states: inserted consumes the completion. Queue-cleared, aborted, and session-replaced or quit receipts retain it and pause automatic retry until later interactive input. Preflight rejection retains it, reports one bounded actionable diagnostic, and retries only at a later session-start or interactive boundary rather than from every `agent_settled` hook. An uncertain receipt is retained, reported once, and never blindly retried, including after input.
- Capability: acknowledged delivery is required and checked before `bg_start` registers or spawns a process. A Pi SDK without `sendMessageWithReceipt` fails explicitly; it never falls back to `sendMessage` or silently disables completion delivery.
- Reload: delivery state is owned by the existing process-global manager and survives extension reload. The manager ABI is versioned. An incompatible manager may be replaced only when no live process or pending completion is observable; otherwise reload fails explicitly and requires stopping/restarting with the live-work prerequisite resolved. No controller, promise, mailbox, or crash/restart durability migration is attempted.
- Retention: cap active and tracked terminals, in-memory output, rendered output, and automatic completion payloads. Spill larger stdout and stderr to private process-local temporary files with a hard byte cap.
- Shutdown: terminals survive `/reload`, `/new`, `/resume`, and `/fork` within the current Pi process. Pi process exit terminates all managed process trees and removes process-local output files.
- Separation from scheduling: do not use background terminals as timers or polling workers. Follow the scheduler contract for long waits.
