# Herdr in the default profile

The default profile owns three deferred tools, `herdr_agent`, `herdr_layout`, and `herdr_pane`, backed by the installed Herdr CLI. No third-party Pi extension is installed. The `herdr` skill dynamically reads `herdr --skill` and adds local workflow conventions rather than copying its manual.

When Pi is inside Herdr, use it automatically for requested long-running development servers and visible logs. New process panes preserve focus. `tool_search` discovers and activates the tools; session replacement hides them again. Descriptions remain short and results are bounded. These process tools provide no background supervisor, service registry, or asynchronous watch daemon. Defined child ownership and normal delegation use the separate [subagent runtime](subagents.md); deferred Herdr agent control complements it for live agents in the connected Herdr server.

## Setup

Install the default profile dependencies and links as described in `pi/README.md`. From the checkout you intend to keep using:

```sh
node scripts/pi-herdr-setup.mjs
```

Setup generates the gitignored default `.herdr-plugin/herdr-plugin.toml` and links `local.pi`. It resolves the actual Node executable and installed Pi `bin.pi`, so rerun setup after moving the checkout or updating Node/Pi. The manifest contains local executable paths, not credentials. Linking registers an executable plugin for the current Herdr user; do not link a disposable worktree into your production session.

Herdr's generated `extensions/herdr-agent-state.ts` is checked in at integration version 9, refreshed with Herdr 0.9.2-preview. Upstream now handles Windows session paths with explicit POSIX and Windows absolute-path checks. Pi's original `reload` lifecycle reason is retained. **Local exception:** settled restricted subagents report `unknown` to avoid completion sounds; blocked operator prompts still report `blocked`. The file header explains this exception. To refresh the generated file after a Herdr update, run `herdr integration install pi` with `PI_CODING_AGENT_DIR` explicitly pointing to default, restore the local exception in the generated diff, and run `pnpm test herdr-agent-state.test.ts` before accepting it. This test fails if the override is lost. Do not overwrite concurrent changes. The repository prompt bridge is separate and must not be copied into generated code. Windows installation resolves the latest official stable Herdr release with 0.9.0 as its fallback minimum. The layout remains compatible with 0.8.x APIs; upgrading a client does not update an already-running server until that session is restarted.

### Agent registration contract

Ordinary Herdr plugin tabs use the process chain `Herdr -> Node bootstrap -> spawned real Pi CLI`, with exact argv and inherited terminal streams and no PowerShell, Bash, or CMD wrapper. The bootstrap owns the pane lifetime and retires its exact `local.pi` pane when the child exits, while the child is the OS-visible foreground Pi process. This identity is required by Herdr 0.9.0 process detection; changing `process.argv` and dynamically importing Pi into the bootstrap hides Pi from Agents. Visible subagents already use the comparable spawned-child host path.

The bootstrap's initial agent report is best-effort early context, not readiness or registration proof. Herdr can return an API `result.type: "ok"` after queuing a report even when terminal-state rules ignore it. Treat exact membership in `herdr agent list` or pane state, matching session identity, and expected lifecycle state as the postcondition.

Reload Pi after source changes. An already-running Pi does not acquire the corrected launcher's process identity or process-exit hook until started through the plugin.

## Tools and process ownership

- `herdr_agent`: list, inspect, read, prompt, wait for, or send logical keys to an exact live agent in the connected server. Agent targets are unique live names or current pane IDs; output and waits are bounded. This does not reach other Herdr servers or machines.
- `herdr_layout`: list a bounded inventory of panes across the complete connected Herdr layout, split beside the calling pane, create a shell tab or workspace, or resume a Pi session. Split/tab and workspace creation use project cwd and preserve focus by default; workspace creation accepts an optional label and explicit `focus`. `{"action":"resume","session":"<UUID>"}` resumes in a focused tab in the caller's workspace, while adding `"placement":"workspace"` creates a separate workspace from the saved cwd, opens the resumed Pi there, and removes the workspace's initial shell pane. Both forms check the exact resumed session identity and return the created IDs. No shell submission is needed.
- `herdr_pane`: read, submit a command, wait for output, rename, move, interrupt, or explicitly close a pane. Move places one non-caller pane in a new tab in an existing different workspace, preserves focus by default, and returns the pane's new ID because cross-workspace moves change it. If the source tab becomes empty, Herdr removes it. Reads default to 80 lines; waits default to 30 seconds and cap at 120 seconds.
- `run` verifies an idle Bash or PowerShell process and its cwd, submits the actual command to existing Damage Control, then rechecks shell identity before sending it once. Unknown shells, missing cwd, unavailable safety gate, denials, or changed targets fail closed. This is not a claim that terminal state cannot race after the final check.
- Raw arbitrary keys/text and agent operations are intentionally absent from `herdr_pane`; use `herdr_agent` for live agents. Do not bypass the tool's safety boundary with `bash("herdr pane run ...")`.
- Explicit operator requests for Claude Code use the shell profile's `ccyl` function in an idle Herdr pane rather than duplicating its provider environment in Herdr. Herdr recognizes the resulting Claude process for prompt, wait, read, and key control by pane ID. Plain `ccyl` uses the saved Claude subscription default; exact subscription selections use `ccyl --model claude-opus-5-5` for Opus 5.5 and `ccyl --model claude-fable-5-1` for Fable 5.1. `ccyl --bedrock` remains explicit opt-in.
- Interrupt/close accepts an exact existing non-caller pane, including panes created by an earlier Pi session. No session-creation ownership record or `confirm: true` field is required. Pi's own pane remains protected. Inspect the connected layout and choose the intended pane; the tool does not classify idle panes as stale or close anything automatically.
- A successful mutation may have empty stdout. It means submission, not readiness or success of the submitted command. On timeout/transport ambiguity, inspect before retrying.
- Waits can match existing scrollback. Use fresh readiness markers or a health endpoint. Output is bounded; CLI output beyond the transport cap fails rather than being silently treated as complete.
- Foreground Compose, detached containers, and log viewers have different lifetimes. Interrupting or closing `logs -f` does not stop detached containers. Cleanup must target the intended Compose project, never a general prune.

## Direct Pi tabs

Inside Herdr, `/new-instance [title]` and `/branch [title]` open a focused plugin tab with the same profile/cwd in the caller pane's current workspace. `/new-instance --resume <session-uuid> [title]` and the `session_launch` tool resume an active-profile session in its saved cwd; an explicit title overrides the saved cwd basename. The launcher resolves the caller's live workspace through `pane current --current` instead of trusting the process's launch-time workspace environment, which can be stale after a pane move. `/branch` extracts the current leaf through a separate SessionManager, leaving the calling parent session ID and file unchanged. It records reciprocal native `session-branch` entries in both sessions with each role, both IDs and paths, and the exact branch-point entry ID and timestamp; these visible records are excluded from model context. They render only one concise line marked `branch parent` or `branch child` with the localized branch time. The full reciprocal evidence remains persisted without adding visual noise or entering model context. The `herdr_layout` resume action reuses this launcher and can supply a newly created workspace explicitly. If separate-workspace launch fails after workspace creation, the error retains that workspace ID; an initial shell-pane cleanup failure is reported without hiding a successfully launched session. UUID lookup examines filenames and the selected native header, not every transcript. Its single tool result contains session, tab/pane IDs, cwd, focus and readiness. Startup checking waits up to 30 seconds for Herdr to report the exact Pi session in an idle, done, working or blocked state. A blocked state means Pi started but needs user input; no input is submitted automatically. Cancellation or unconfirmed startup returns the created tab's IDs and `ready:false`, not a second launch. This resumes an independent interactive session, not a delegated subagent. The plugin bootstrap makes a bounded, best-effort registration of the new pane with Herdr's agent list and waits for an acknowledged matching response before starting Pi. Registration failure does not prevent Pi startup. The generated lifecycle extension subsequently attaches Pi's session identity and live state. Branch launch passes the exact created session file. Launch failures retain that file and report a resume path; an ambiguous result never automatically submits another launch.

The default profile's `/plans` selector prepares or verifies the highlighted direct-child `.specs/<stub>/plan.md` task worktree before launching `/do-it` there in a focused Pi plugin tab. Preparation records the actual task checkout/branch and originating checkout/branch, carries the whole selected spec including uncommitted supporting files, and preserves newer resumed task progress and unrelated source work. Herdr's native worktree open/reuse groups that checkout, rather than using a tab title as Git provenance. Only a known newly created initial shell is removed after the Pi pane exists; existing user panes stay open. Preparation/launch failures report retained coordinates, not automatic deletion or a second launch. The runtime supplies prepared coordinates so `/do-it` does not create another task worktree. Pi consumes the launch receipt at session admission and persists it for that exact session; reload restores the metadata, while an ordinary new Pi process cannot inherit prepared status through the environment. The lasting active profile and explicit plan title remain unchanged. Direct `/do-it`, run here, ordinary new/resumed/branched sessions, and non-Herdr execution keep their existing paths. Pressing `d` shows Launching in the existing picker before starting process work. Herdr Pi-tab requests are asynchronous and bounded; the launcher explicitly focuses the exact returned tab instead of relying on creation defaults. Repeated input is ignored while the request is pending, and success dismisses the originating picker rather than reopening Details. Focus is not restored to the origin.

Safe prelaunch failures preserve the view and selection and allow retry. A timeout, uncertain response, or failure after tab creation warns that the launch may exist and is not retried automatically. Tab creation/focus alone is not a readiness acknowledgment from Pi or proof that the model has begun executing the plan.

New-tab execution is unavailable outside Herdr and has no terminal fallback. The plugin bootstrap accepts only the constrained repository-relative plan path, validates it under the launch cwd, and constructs the `/do-it` message itself. It does not accept arbitrary initial prompts or argv. `/plans` action requests and outcomes are appended as native custom session entries and excluded from model context. The initial invocation event remains available to analytics but is not rendered because the shared command row already shows `/plans`; subsequent action events render as compact transcript rows. The plan child receives the selected stub as explicit title metadata; because plugin-tab creation has no label option, child startup applies that title to the tab while preserving the plugin pane label. Run here renames only the inherited `HERDR_TAB_ID` and still submits execution if naming fails. Native Pi persistence applies: a fresh picker-only session may not reach disk before an assistant message, so analytics cannot recover an unsaved session.

The process chain is Herdr → Node running the repository bootstrap and Pi. No PowerShell/Bash/cmd wrapper is used. The bootstrap runs the existing default Damage Control syntax preflight; failure enters tools-disabled/extensions-disabled repair mode. Ordinary tabs accept only profile and optional session inputs, not arbitrary extension/tool flags or automatic recovery. Restricted subagents additionally supply a per-child authenticated endpoint; the bootstrap obtains the frozen assignment from its parent and constructs the restricted argv itself. A per-launch host owns the child process handle and terminal streams. A failed safety preflight rejects a restricted launch rather than entering an unrestricted or misleading repair conversation.

The installed preview can replace an exited focused terminal with a shell. The bootstrap explicitly retires its own `local.pi` pane at process exit to prevent this. It does not close other panes or stop services. `/new-terminal` still opens a shell, and non-Herdr Windows Terminal/Ghostty launch behavior is unchanged.

## Defined subagents

`subagent` uses native TUI children by default inside Herdr, with an explicit headless override. It verifies the configured `local.pi` bootstrap belongs to the active profile's repository and owns only returned pane IDs. Ordinary children occupy two rows of five panes left-to-right above the original caller, which remains full-width below them at approximately two-thirds of the total height for one through five children and one-third once six through ten children require the second row. The eleventh child starts a named overflow tab; each ordinary overflow tab repeats the two-row group of ten. Team Leads reserve exclusive rows with visible descendants beside them. A growing team uses a second free row or moves intact to a dedicated tab with the leader as its bottom anchor; a shrunken clean team returns when origin capacity permits. Nested Team Leads form their own groups. Lifecycle-triggered reconciliation is serialized and does not poll. Visible launch resolves `pane current --current` before placement instead of treating the process's launch-time `HERDR_PANE_ID` as authoritative; an empty failed layout group can rebind only when the caller terminal identity is unchanged. Manual geometry detected at a later lifecycle boundary marks that managed tab dirty, suspending automatic resize and migration without giving up pane ownership or cleanup. Same-workspace moves preserve verified terminal identities and update runtime pane IDs from Herdr's response; ambiguous moves stop without recreating a process. Herdr only exposes downward plugin splits, so the first child is swapped above the caller. The swap temporarily focuses the caller; the adapter restores the previously viewed pane through the public exact-pane focus API unless it observes a subsequent user focus change. This is best-effort restoration, not atomic non-focusing placement. Later splits and migrations use `--no-focus`. Ordinary child roles have no general Herdr control tools. Team Leads can discover and activate the three deferred Herdr tools within their frozen authority. Ordinary parent chat changes preserve separate subagent ownership, but explicit `/reload` is supported only when no active or idle retained child remains and replaces the executable runtime owner. Process-pane control is a complementary connected-server path, not a substitute for owned-child lifecycle controls.

Assignment results travel through authenticated local messages, not terminal scraping or Herdr status. Finished panes close immediately after result capture and process settlement, even if that removes zoom elsewhere. Direct user help suspends parent steering and requires explicit handback. Parent exit stops ordinary children but preserves directly helped visible children as parent-unavailable. See [authority, controls, and validation](subagents.md).

## Prepared-plan closeout successor

For integrated prepared runs only, `closeout_successor` launches a restricted Integrator in a new pane of the exact live tab, with the recorded parent checkout as cwd. Its launch-owned host survives the originating orchestrator; this is not ordinary retention, user intervention, or a general detach API. The successor-only extension is inert during ordinary resource discovery and binds its authenticated surface only in admitted successor mode. The same local manifest bounds integration and cleanup, with no delegation, push/deployment, branch deletion, or broad Herdr control authority.

The Integrator first integrates, restores unrelated work, and commits/verifies completion metadata, reporting `INTEGRATION READY` while the worktree remains. The orchestrator finishes any explicitly authorized orchestrator-only obligations before release. Successful release cancels further originating-model continuation even when it shares a tool batch or is called through codemode. Exact graceful shutdown remains settlement-bound; the successor observes Pi/bootstrap exit and pane retirement before removing the task worktree and giving the final outcome-first operator report. Its pane remains available with parent-checkout cwd even though the workspace originated from the removed worktree. Cleanup does not close its tab/workspace or rename away the plan title.

Before retirement, blocked integration or a consequential decision keeps both panes and the worktree available; the successor accepts native operator input and the orchestrator avoids concurrent target mutation or duplicate reporting. After delivery, retirement/removal failure reports `CLEANUP PENDING`, verified delivery and the exact retained path. No rollback, orchestrator recreation, server restart, or extra approval ceremony is introduced. `--no-merge` excludes successor mutation and retirement and intentionally retains the task checkout. Ordinary/direct Integrators keep one-shot cleanup and parent-owned questions/reporting. Source edits do not upgrade an active session; use the normal settled-only activation boundary.

## Automatic session tab naming

The default-profile Herdr orchestrator may quietly name its tab from the current conversation. Naming is limited to the first delivered user prompt and later settled turns, with at most one attempt per 60 seconds measured from the previous attempt's start. A restored session (including a resumed child) gets one asynchronous attempt from its restored ordinary user/assistant text; it does not wait for another prompt and does not delay readiness. Requests use the latest authenticated `openai-codex` Luna in tool-free completions at low reasoning with provider retries disabled. Only bounded recent visible user text and ordinary assistant prose are supplied; thinking, tools/results, instructions, logs, summaries, and unrelated sessions are excluded.

Generated titles are normalized to lowercase and must be one to five plain words. An empty model response, or a valid response equal to the current title, is an intentional no-op. The model does not provide a deterministic fallback, placeholder, alternate model, or deferred retry. `/rename <title>` applies and protects an explicit title literally, while bare `/rename` immediately reclaims the current tab and requests a contextual title regardless of the automatic cooldown, breaker, or prior manual protection. Command-requested outcomes are reported in the UI. Explicit titles from `/plans`, `/branch [title]`, and `/new-instance [title]`, plus an observed manual Herdr rename, are preserved literally and suspend automatic naming until `/clear`, `/new`, or a bare `/rename`. The cwd basename is used as the initial/default title, and `/clear` and `/new` cancel stale work, restore that basename, clear manual protection, reset the cooldown and failure breaker, and start a fresh naming owner. `/reload` preserves ownership, cooldown, and breaker state. Separately, owned subagent overflow tabs show the agent's name and role when alone, such as `Elena · reviewer`. When shared, they use the origin tab label captured at first overflow plus numbered suffixes such as `· agents 2` and `· agents 3`. Joins and departures update the title, including restoring a remaining singleton's name. Before updating an existing title, the layout checks it against its last applied title; a detected manual rename permanently stops these updates for that tab. This check is best-effort, not atomic with renaming. Caller and unrelated tabs are never renamed. This does not use the model or automatic session naming subsystem.

Model, Herdr, validation, and timeout failures are counted silently. Three consecutive automatic-attempt failures open a breaker; there is no timed recovery or half-open probe. Lifecycle cancellation and ownership changes are not failures, while a title change detected before or after the model call pauses naming rather than overwriting it. Foreground chat, resume receipts, focus, and readiness do not wait for naming. Diagnostics are best-effort structured JSONL at `$PI_CODING_AGENT_DIR/runtime/herdr-tab-naming.jsonl` (the active profile's `getAgentDir()` runtime path), retained to at most 64 KiB and 128 complete lines. Response/error evidence is bounded and redacted; credentials, environment contents, raw tool history, and transcript entries are not logged. Routine successes and failures are silent; only an unexpected internal extension fault may produce one warning.

Live verification is non-blocking and opt-in: `PI_SUBAGENT_UX_LIVE=1 pnpm test subagent-ux-live.test.ts` uses only an isolated Herdr server/config/plugin registry and inert processes. It checks five-wide geometry at the 1/5/6/10/11 boundaries, overflow through 21 panes, exact pane and process identities, focus, team migration to a dedicated tab, and automatic return after shrinkage. The fixture follows the isolated configuration's actual running session name because current Herdr previews may start that isolated server as `default`. It does not establish attached-client rendering, keyboard focus experience, or production-pane acceptance. Earlier four- and eight-pane probes are historical. Source changes do not alter already-running Pi sessions; use the normal settled-only activation boundary.

## UI and attention

On initial interactive Pi startup inside Herdr, the default profile labels its inherited pane **Orchestrator** and its inherited tab with the working directory's basename, for example `.dotfiles`, without changing focus. Explicit plan children are identified by `PI_HERDR_TAB_LABEL`; startup keeps their plugin pane label and applies the inherited explicit title to the tab because plugin-tab creation has no label option. Restricted subagents keep their human assignment labels and do not rename tabs; RPC/print helpers do not rename either surface. New, resumed, forked, and reloaded chats within the same process do not reset user-renamed panes or tabs. Label failures are silent and do not block startup. These labels do not change agent identity.

Herdr owns sidebar symbols and colors. In Herdr 0.9, working is yellow, blocked is red, idle is green, and an unfocused completed idle transition may appear as client-relative teal done until that client views it. The default profile reports lifecycle state rather than trying to choose those visual states.

The existing footer, reload indicator, dialogs, and notices remain Pi-owned. Automatic naming adds no footer badge, transcript row, notification, bell, or model-context state. The generated Herdr integration publishes TUI working/settled state. The repository bridge maps native prompt start/end to operator-waiting state, including the current Damage Control custom dialog. Headless helper sessions do not claim the parent's pane.

There is no additional bell or desktop-notification layer and no sound/desktop settings change. The repository's local exception to Herdr 0.9.1 integration version 9 reports settled restricted subagents as `unknown`, avoiding background completion sounds while their results reach the parent and their panes close. Actual operator prompts still report `blocked` and retain Herdr's request sound. Orchestrator lifecycle reporting is unchanged. In the isolated live test, an unfocused actual approval dialog reported `blocked`; denial cleared the orchestrator to background `done`. Headless API evidence does not prove audible or desktop delivery. Those require an attached client and operator observation under the user's Herdr settings.

## Validation

From `pi/profiles/default/`:

```sh
pnpm test herdr-tools.test.ts herdr-resume.test.ts herdr-launch.test.ts session-launch.test.ts herdr-ui-prompt-state.test.ts tool-visibility.test.ts tool-search.test.ts
pnpm run typecheck
pnpm run check:runtime
```

Plan checks live in `plans.test.ts`, `session-launch.test.ts`, and `herdr-launch.test.ts`. Run `PI_PLANS_HERDR_LIVE=1 pnpm test plans-herdr-live.test.ts` from the default profile for a real launch in an isolated Herdr session. It verifies immediate feedback, one focused native worktree tab, original-picker dismissal, actual `/do-it` expansion and session-owned prepared admission without executing a real plan. `PI_PLAN_CLOSEOUT_HERDR_LIVE=1 pnpm test plan-closeout-herdr-live.test.ts` exercises the production origin facade and lifecycle, real successor host/surface and canonical helper for success, integration blocker, cleanup failure and mixed-batch release. Deterministic providers replace reasoning/network, not admission, tool routing or shutdown handlers. Attached-client rendering and real-provider behavior remain separate validation limits.

Live acceptance uses isolated named Herdr sessions, an isolated config/plugin registry, and uniquely named disposable Compose projects. Pin the test socket explicitly: merely overriding config paths while inheriting a production `HERDR_SOCKET_PATH` can route plugin operations to the wrong running server. Never stop a shared server. Tests distinguish CLI submission, actual readiness, and user-observed notifications.

The 2026-09-13 registration evidence used Windows, Node v25.9.0, Pi 0.85.1, and Herdr client/server 0.9.0. The isolated direct-tab test passed exact registration with the Windows session path, idle -> working -> done transitions, same-session reload, native input, and exact cleanup after child termination. The visible/headless test passed newly added exact registration, state, session, and headless-exclusion assertions, then failed later at a pre-existing unrelated `userOwned` assertion; unmodified main reproduces that same later failure. Do not interpret that run as the entire subagent live suite passing, and do not treat unit tests as proof of visibility. Full shared-server restart or Herdr upgrade was not required by the evidence.

Detailed reproduction IDs and boundaries are recorded in [the archived plan](../../../.specs/archive/herdr-complete-pi-agent-registration/plan.md) and [experiments.md](../../../.specs/herdr-complete-pi-agent-registration/experiments.md). Windows process identity and these isolated server checks passed; Unix signal/process-group behavior, attached-client visual rendering, every transient lifecycle interleaving, and audible/desktop notifications remain unverified.

Persisted plan history uses the existing `session_entries` view. Outcome counts:

```sql
WITH plan_events AS (
  SELECT json_extract_string(record, '$.data.action') AS plan_action,
         json_extract_string(record, '$.data.outcome') AS plan_outcome
  FROM session_entries
  WHERE entry_type = 'custom'
    AND json_extract_string(record, '$.customType') = 'plan-action-event'
    AND json_extract_string(record, '$.data.phase') = 'outcome'
)
SELECT plan_action, plan_outcome, count(*) AS records
FROM plan_events
GROUP BY plan_action, plan_outcome
ORDER BY plan_action, plan_outcome;
```

A chronological invocation trace is bounded to one session reference selected through `sessions` discovery:

```sql
SELECT _timestamp,
       json_extract_string(record, '$.data.invocationId') AS invocation_id,
       json_extract_string(record, '$.data.action') AS action_name,
       json_extract_string(record, '$.data.phase') AS phase,
       json_extract_string(record, '$.data.outcome') AS outcome_name,
       json_extract_string(record, '$.data.plan.stub') AS stub
FROM session_entries
WHERE entry_type = 'custom'
  AND json_extract_string(record, '$.customType') = 'plan-action-event'
ORDER BY _timestamp
LIMIT 200;
```

These queries cover persisted native entries only. A picker-only session that Pi never saved has no analytics record.
