# Quiet commits

`/commit` runs the private Git workflow directly from its command handler. `/commit push` also requests publication. F10 invokes `/commit`; F9 invokes `/commit push`. These are operator conveniences, not the route for ordinary conversational commit or push requests, which the main agent handles with Git through Bash.

There is no main-agent commit tool, tool discovery, hidden commit prompt, or model-selected dispatch. The command calls the in-memory Terra runner directly. `/bro` remains prompt-backed. Legacy is unchanged.

## What you see

- The command invocation and Pi's standard animated loader above the editor, with phase messages for waiting, inventory, model resolution, review, plan validation, execution, and result collection. It stays non-modal so ignore questions work, and stops on completion, failure, or cancellation. RPC uses status text instead.
- Obvious generated artifacts and caches are excluded without a question, even if no ignore rule covers them. New additions matching existing ignore rules are excluded by default. Completion reports skipped paths and their reasons; working files are preserved.
- Ignore questions only for genuinely consequential inclusion ambiguities or concrete reasons to intentionally include ignored new files, with `Include in commit`, `Add to .gitignore`, and `Leave untracked` choices. Questions happen after staging. Adding a rule updates and stages that repository's `.gitignore` and unstages the candidate without deleting its working copy. Leave untracked also unstages it; Include keeps it eligible. A filename containing `.local` alone does not require a question. Cancelling the question stops the workflow.
- Brief retry and repair progress. Routine errors, failed local Git operations or hooks, newly discovered work, and publication problems return to the reviewer for diagnosis, repair when safe, and a fresh plan. User decisions or access that the agent cannot resolve, terminal provider failures, cancellation, deadlines, and unconfirmed push outcomes still show an error and actual Git state. Successful commits are not undone.
- One displayed completion entry containing actual short hashes and commit subjects, plus `Pushed` only when Git confirms publication and the workflow is complete. Remaining changes, skipped files with their reasons, preserved index references, or errors appear when present. If nothing was committed, the result says so. The same outcome is persisted in model context without starting an extra turn, so the main model can explain failures on your next message. It is not asked to present the result or repeat Git work.

The command waits for an active main-agent turn to finish before starting Git work. Shortcuts use the same idle boundary rather than rejecting busy input. Escape cancels a waiting or running command; session shutdown also cancels it. Existing ignore dialogs retain their normal Escape behavior. Temporary progress and input listeners are cleared after completion, failure, or cancellation.

## Review and execution

The AI proposes a structured commit plan. Runner code stages, validates, executes, verifies, and publishes it. The AI reviews staged diffs and repository instructions, chooses related whole-file groups and subjects, and gives concrete reasons for exclusions. Groups and messages need no approval. Unclear grouping defaults to one sensible commit. Tracked feedback records are ordinary eligible changes; a record's lack of independent commit authority does not override `/commit`.

Before review, code preserves sole index-only content in a retained Git stash when staging would overwrite it. It uses `git stash create` and `git stash store`, constructing an equivalent index snapshot when Git omits submodule-only changes. The retained reference is reported, not applied or dropped. Code runs `git add -A`, respecting normal ignores, applies the fixed settings policy, and stages required child gitlinks. Outside the dotfiles repository, the settings policy adds the exact `.pi/settings.json` path to the repository's `.gitignore`, unstages that settings file, and stages `.gitignore`.

The reviewer must honor `.gitignore`, `.git/info/exclude`, and global Git excludes, including during publication conflict resolution. It may not force-add ignored files, weaken or disable rules to include them, or otherwise bypass exclusions without discussing the specific paths and reason and obtaining explicit user approval. General implementation, archival, `/commit`, or `/commit push` authorization does not approve an exception. Staged additions are checked with `git check-ignore -v --no-index` so earlier forced staging cannot hide a matching rule. Matching additions are excluded by default, not routed automatically to a question. The reviewer also uses ordinary Git judgment to exclude obvious generated artifacts through the existing commit plan without needing an ignore rule. Only a genuinely consequential inclusion ambiguity or a concrete reason for an intentional ignore exception warrants `ask_ignore`; an informed `Include in commit` answer approves only that candidate. Existing tracked modifications are not automatically untracked or excluded just because an ignore rule matches. This is agent guidance, not a new runtime enforcement mechanism. The private reviewer prompt is read on each invocation; refreshing the profile-wide instructions requires a fresh session or `/reload`.

Normal review tools are `submit_commit_plan`, read-only `inspect`, `read`, `ask_ignore`, and `report_commit_blocker`. There is no normal mutation `bash` or `publish_repository` tool. The runner temporarily offers `bash` for a reported repair or publication conflict. `ask_ignore` accepts only staged new files, not tracked modifications. Invalid arguments return for correction without a dialog. An ignore mutation failure returns to the agent with repair tools while preserving the operator's exclusion choice; required user input in noninteractive mode and cancelled dialogs still stop work. Code applies answers and refreshes status for plan validation.

The plan has this shape:

```text
{ repo, commits: [{ subject, paths: string[] }], exclusions: [{ path, reason }] }
```

Paths are repository-relative and must match current Git status. Every changed path, including staged gitlinks, must appear exactly once in a commit or an exclusion. Rename endpoints must stay in the same commit or both be excluded. Code rejects missing, unknown, duplicate, empty, absolute, or parent-traversal paths, unresolved conflicts, empty groups, invalid subjects, and exclusions without reasons. Subjects must be trimmed, nonempty single lines. An empty commit list is valid only if every changed path is excluded or the repository is clean.

Validation returns specific errors to the same agent for correction within the existing active-work deadline, without a fixed two-correction limit. No part of an invalid plan is committed. If review ends without a plan while changes remain, the runner asks the agent to finish the plan or report a concrete blocker. A clean repository may finish without a plan as a no-op.

For an accepted plan, code builds each group's index from the reviewed staged contents, leaving exclusions unstaged and preserving working contents. It commits with normal hooks, verifies that HEAD advanced, and checks that the resulting commit contains exactly the reviewed paths. A failed group stops execution of that snapshot, not the entire workflow. The agent receives diagnostics, actual completed commits, and remaining work; code refreshes staging and requests a new reviewed plan. Successful repair-shell calls also refresh staging before further review. This handles new files, hook edits, and partial completion without blindly replaying old groups. Preparation failures get a repair-only turn before staging is retried.

The agent may fix clear local causes but must not bypass hooks, weaken ignores, discard work, change credentials, rewrite history, or exclude eligible changes to hide an error. `report_commit_blocker` ends the workflow with the concrete decision or access it cannot resolve. Any unfinished eligible changes still prevent success and publication; only applicable unstaged exclusions may remain. Final result collection also checks for unfinished work. There is no rollback or atomic transaction; actual earlier commits and publication outcomes remain reported after a later failure.

## Repositories and publication

Code selects initialized repositories deepest-first for scoped passes. Each repository starts with a fresh reviewer transcript and its own working directory for shell inspections and relative file reads. Only the current repository's candidate status and instructions are included; other inventory entries provide boundary names, not competing candidate lists. Children finish review, commits, and requested publication before the parent's pass. The runner compares immediate child HEADs with the parent's committed gitlinks and stages required pointer updates for the AI to include in the parent plan. It does not commit unreviewed pins. Distinct index-only/conflicted gitlinks, explicit exclusions, and staged submodule removals/replacements are respected. Local child and parent-pin commits require neither pulling nor publication. Detached repositories remain eligible for local commits but are silently skipped for publication.

Bare `/commit` performs no publication-related branch, upstream, outgoing, remote, or push checks. `/commit push` captures its push choice directly from the command arguments. After a successful repository pass, code checks outgoing commits and publishes attached repositories that need it, including otherwise clean children with outgoing commits. Children publish before parents.

Code runs `git pull --no-rebase --ff origin <own-branch>` before `git push --recurse-submodules=no origin HEAD:refs/heads/<own-branch>`. Git fast-forwards where possible and creates a merge on divergence; history is not rewritten. The publication helper refreshes parent gitlinks before pulling and after integration. Missing pins return to staged review and plan execution before any parent push. The runner does not push the same unchanged HEAD twice and verifies uncertain push outcomes against Git. Force-push, tags, and other branches remain excluded. This command option does not limit separately authorized ordinary Git work.

When a publication pull establishes merge conflicts, the runner offers a scoped mutation `bash` tool instead of plan and ignore tools. The AI may inspect, resolve conflicts when intent is clear, stage resolved paths, and commit the merge with normal hooks. It does not pull or push. Code verifies that a merge commit was created and conflicts are resolved; additional eligible changes return to ordinary staged review. Non-conflict publication failures get a repair-only turn and a refreshed review before code retries publication. Unconfirmed push outcomes are not blindly retried.

## Repository IDs and filesystem paths

Inventory entries, plan targets, ignore decisions, and result labels share the repository-ID helpers in `lib/path-identity.ts`. IDs use forward-slash separators, for example `modules/onclave`, with `.` for the root. On Windows, private-tool repository lookup and ignore-candidate paths also accept native backslash spelling. On POSIX, literal backslashes and case remain significant. Lookup stays limited to discovered inventory entries; normalization does not resolve arbitrary paths or change publication eligibility.

Native absolute paths are retained separately and passed to filesystem and Git operations. Windows, Git Bash, and WSL path conversion is not done by rewriting repository IDs. Existing absolute-path comparisons use the separate platform-aware helper.

## Implementation and limits

`extensions/commands.ts` calls `runCommitReviewer()` in `commands/commit/reviewer.ts`. The runner owns one awaited, in-memory Pi `Agent`, uses the profile's catalog/auth, and supplies repository inventory, initial status, tracked AGENTS.md paths, the selected repository, and the absolute repository root. `commands/commit/plan.ts` validates and executes whole-file plans. Model selection uses the latest available Terra through the native OpenAI subscription at medium effort, with the existing latest Anthropic Haiku fallback at low effort; the selected conversation model is unchanged.

`inspect` uses the native Bash tool for normal Git commands, searches, and focused discovery. It returns nonzero results to the reviewer for interpretation or correction, including compound commands, pipes, search no-matches, and `git check-ignore` exit 1 (not ignored). Read-only tool guidance is not a shell sandbox. A failed repair or conflict-resolution mutation stops queued calls from that response, then returns its full diagnostics to the agent for correction on the next response. Command tails and original whitespace are preserved.

The three-minute active-work budget pauses during ignore questions. Git reads, plan execution, and shell commands retain 15-second timeouts. Pulls and pushes use the 120-second publication timeout. Transient response failures share three retries with 1s/2s/4s abortable backoff. Completed tool history is retained within the current repository pass. Git and hook failures are not blindly replayed: the agent inspects the result and revises its approach. All correction and repair passes share the same active-work deadline; cancellation and terminal provider failures remain terminal. No new tests, lint, builds, secret scans, approval steps, or other gates run as part of `/commit`.

After failure or cancellation, read-only queries report actual commits and remaining status without reusing the cancelled signal. Those queries may extend wall time. Private agent calls and reasoning do not enter the main conversation. Final results, including full failure diagnostics, enter model context as hidden custom messages with `triggerTurn: false`; the existing interface entry supplies the single displayed result. No child session/report files are saved.

Run `/reload` after code changes to load this behavior in an existing Pi process. Deterministic-provider tests use the real Agent lifecycle and temporary real Git repositories for staging and publication semantics. They do not establish live model judgment or attached UI acceptance.
