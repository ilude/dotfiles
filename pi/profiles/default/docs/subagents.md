# Subagents

## Select the host backend

The default profile uses the existing native backend in standalone Pi and Herdr, and an app-owned T3 backend when Pi is launched by T3 Code. Plain RPC or inherited T3 environment markers on a native child do not select T3 ownership. The shared Markdown roles, trusted project overrides, model/effort defaults, skill selection, and frozen tool/delegate policy stay Pi-owned.

| Operation | Standalone Pi / Herdr | Pi in T3 Code |
| --- | --- | --- |
| Named role launch | `subagent` | `t3_delegate_role` |
| Owned child control | `subagent_control` | `t3_role_control` |
| Child question / unfinished report | `subagent_parent` | `t3_role_parent` |
| Lifecycle and delivery | Native profile runtime | Existing T3 tasks, threads, runs, questions and results |

### Opus and ccyl routing

- **Work-project Opus tasks** use Pi/AWS Bedrock. **Personal-project Opus tasks** prefer ccyl with the personal Claude subscription, for implementation as well as advice or review. Explicit route requests take precedence. This is agent guidance, not a hardcoded project classifier: use the task's project context and existing Git identity; `git config --show-origin --get user.email` in its repository can identify the personal/professional include. Unknown, sentinel, or mixed-project context needs clarification, not a guessed account. Do not silently switch accounts on failure.
- **Pi model resolution stays unchanged:** passing `model: "opus"` selects AWS Bedrock with the requested effort; the newest configured Mantle Opus wins, then native Bedrock if Mantle has no configured match. `/opus` still selects the active Pi model through this AWS family resolution; it does not migrate the conversation into Claude Code.
- **ccyl Opus high** selects T3's configured `ccyl` Claude Code provider, its advertised subscription Opus model, and `target.options.effort: "high"`. **Use ccyl** without a model keeps its effective Claude subscription default, resolved from its settings and advertised catalog rather than inherited from Pi. Do not enable ccyl Bedrock mode unless separately requested.
- The orchestrator chooses the external-client route before dispatch, using generic T3 `delegate_task`, not `t3_delegate_role`. A later explicit ccyl request after a failed Pi-role attempt also selects a new external-client task, not an automatic role fallback. Keep the bounded assignment and disclose that Pi's frozen role/tool enforcement does not carry over. ccyl may perform any authorized task type; if Pi-specific enforcement or capabilities are required, report the incompatibility. Pi-bound children return ccyl needs to the orchestrator rather than bypass their own authority. Native/Herdr ccyl launch mechanics remain unchanged.
- **Council preference:** Sol, project-routed Opus, and Grok through AWS. AWS Grok is permitted for both personal and work projects. Resolve actual available models before dispatch; the separate T3 `grok` provider is not the AWS route. AWS Grok has not yet been live-verified here. The orchestrator owns any ccyl Opus seat and supplies its findings to the non-writing council.

#### Claude subscription quota

Use the deferred `claude_usage` tool when planning ccyl work. It reads the existing Claude OAuth login in place and fetches account-reported five-hour, weekly, and available Opus-specific weekly percentages and reset times. Results include `fetched_at`, `config_dir`, and the usage-page link. These quotas are shared across sessions and clients, not a per-task allowance or something token costs can reconstruct.

The default credential directory is `CLAUDE_CONFIG_DIR`, otherwise `~/.claude`. When the selected ccyl client's directory differs from Pi's environment, pass its exact absolute directory as `config_dir`; do not treat another account's headroom as ccyl's. The currently checked T3 ccyl instance uses `~/.claude`. The tool does not copy, refresh, or persist credentials, initiate login, poll, or enable paid overage. Missing/invalid windows are null, not zero; failed requests are errors, not evidence of free capacity. File-based credentials are supported; OS-keychain-only logins are not implemented.

Reuse a recent observation; refresh after substantial ccyl work or a reported limit. Report exhaustion with the observed reset time and ask whether to wait or use another authorized route. No fixed warning thresholds, automatic fallback, or background monitor is introduced.

Pi launch tools describe bare-name selection and reject an explicit `anthropic/...` override unless the caller also supplies `providerOverride: "anthropic"` for a user-requested direct provider. An override must match a supplied `provider/model`; `ccyl` is rejected as a Pi model/provider. This makes the override deliberate, not proof of user intent: the agent still must follow the routing instructions. Explicit configured role defaults and other existing provider-qualified references remain unchanged. Route failures are reported without silent substitution or an unrelated login request.

### Named Pi roles in T3

`t3_delegate_role` launches a Pi-enforced named role, not a generic category in T3's `delegate_task`. The orchestrator still has the unchanged raw T3 tools for genuinely generic operations. Named-role operations must use the profile wrappers, even for the same provider, worktrees, or background execution. An unsupported role launch is an error, never permission to bypass it with raw delegation, a different model, a CLI, or a hidden native child.

The launch fields are `agent`, `instructions`, optional `model`, `providerOverride`, `effort`, `skills`, `background`, `blockingReason`, `isolation`, `title`, and `timeoutMs`. Explicit settings override role defaults subject to existing constraints. Pi resolves models to provider-qualified references; the parent's current Pi instance must offer that model. Advertised T3 `thinking` options are passed explicitly. Custom/fallback catalogs can omit those descriptors, in which case no unknown T3 option is sent. Pi bootstrap always applies and verifies the exact frozen effort before the first request. It does not inherit the parent's model/effort as a substitute. Selected skill sources remain frozen; project-relative resources rebind to the actual child checkout and still require that checkout's project trust.

Foreground is the default. Strategist is always foreground, including when `background: true` is passed. Every other foreground launch requires `blockingReason`: why no useful independent work remains and why automatic delivery after returning control is unsuitable. A downstream dependency alone is insufficient. Use `background: true` for automatic T3 results while doing independent work or returning control. `timeoutMs` bounds a foreground wait, not the child's assignment. Interrupted or expired waits leave work live. Follow T3's returned `next` instructions without status polling, sleeps, watchers, or scheduled wakes.

```text
t3_delegate_role({agent: "strategist", instructions: "Recommend bounded assignments for the authorized task."})
t3_delegate_role({agent: "developer", instructions: "Implement the assigned bounded change.", background: true, isolation: "shared"})
```

A returned `launchId` identifies the frozen role conversation. `threadId` identifies its T3 child thread; `taskId` identifies the current assignment; `runId` identifies a T3 execution. A retained-thread assignment can have a new task ID. `piSessionId` is supplied only when actually known, never inferred from a T3 identity. Readable titles start with the role and brief, and append `[pi-role:<launchId>]` so ownership can be resolved from public parent activity while a blocking launch is still waiting. Mention returned child links verbatim rather than synthesizing links or using bare IDs as navigation.

`t3_role_control` takes `id` (returned launch ID, child thread ID, or owned task ID) and an action:

- `inspect` reads the saved task result; `read` reads the child thread. These retrieve evidence, not a monitoring loop.
- `wait` is one event-driven terminal rejoin, not a question wake, with required `blockingReason` and optional `timeoutMs`. It does not cancel on interruption.
- `message` sends `message` with `mode: auto|queue|steer|restart` (default `auto`). It steers/continues the retained role and reports a new task ID when one is created. Optional `freshContext: true` replaces Pi context without replacing the frozen role. Dispatch acceptance is not completed work. New review/re-check assignments require a fresh `t3_delegate_role`, not a message; council rebuttal can reopen its existing members.
- `questions` lists pending user questions, or reads one with `requestId`. `answer` takes `requestId` and an `answers` object in the pending request's format. Neither operation grants permission approval.
- `cancel` stops the current owned assignment, queued turns, and descendants through T3. Old results remain readable. T3 can refuse when a user has raised a child's permission/interaction modes beyond the caller's ceiling.

`t3_role_parent` is available only when the role permits its canonical parent tool. `action: "question"` with `message` uses blocking Pi `ctx.ui.input`, mapped to T3 user input. Only the questioning child pauses; the parent and other children continue. T3 notifies the parent, which may answer from known instructions through `t3_role_control`, ask the user, or let the user answer in the existing UI. This is not native yield-and-discuss: there is no `cancel-question` or permission-answer action. A process-lost dialog may need re-presentation with a new request ID.

Use a normal final reply for successful work. `action: "report"`, `message`, and `outcome: completed|partial|blocked|failed|cancelled` preserve a substantive role outcome without terminating execution or changing T3's status. Genuinely partial/blocked work should also say so in its normal result text. Wrapper results distinguish `t3Status` from `roleOutcome`; an ended execution is not proof of successful work. T3 owns result delivery, child settlement and UI. There is no second result/status ledger, duplicate native completion message, custom role badge, or custom T3 terminal status.

### T3 authority, workspaces, goals and closeout

The private `/t3-role-bootstrap` command consumes profile-owned handoff metadata and authenticates the actual child's thread/lineage before dispatching its stored assignment. Its opaque launch reference is not a credential. Tool/delegate policy is checked at dispatch as well as in the prompt, including discovered tools, codemode, and raw qualified T3 operations. Internal wrapper calls get an exact, single-operation grant, not unrestricted raw-tool access. Full access does not disable Pi authority or Damage Control. Explorer remains inspection-bound. These restrictions are not an OS sandbox.

T3 loads its normal configured Pi profile; it does not provide native per-task extension-isolation CLI flags. Role composition preserves the actual project's loaded context and trust, replaces caller routing with the selected role and permitted catalog, and supplies only selected skill bodies rather than unrelated discovery catalogs. Shared role definitions and native automatic discovery remain unchanged. The installed generated bridge is not patched: its generic routing is scoped to root generic operations, and removed from role requests after its prompt hook. Role snapshots and thread bindings restore frozen authority after reload/resume or fresh Pi context; copied history does not establish ownership in an unrelated thread.

`isolation: "shared"` (default) uses the commissioning thread's checkout. `isolation: "worktree"` asks T3 for a **new** checkout from the parent's HEAD. There is no arbitrary `cwd`, existing-worktree selector, unrelated local project, or remote role-handoff parameter. A shell `cd` or shell-created worktree does not bind a T3 thread. Missing workspace/resource/settings support is an explicit error, not silent substitution.

Integrator accepts only the existing runtime-issued, validated closeout manifest. Its commissioning T3 thread must already be bound to the manifest's **exact target checkout**, and it uses shared isolation; bootstrap validates the target again. The existing manifest validator also requires the task worktree under `repositoryRoot/.worktrees`. Other task-worktree locations remain unsupported, rather than being widened for T3. `--no-merge` never authorizes mutating closeout. T3 Integrator returns normal typed outcomes to its parent, which retains questions and final reporting. Herdr's same-tab successor, exact-origin retirement and pane cleanup are not available in T3; no top-level thread or native fallback is created to work around a mismatch.

Goal inheritance reuses the canonical goal admission, membership, baseline and finalized-usage accounting, including nested descendants and the inherited original scope. An unavailable owning goal/admission endpoint blocks work rather than dropping the budget. Explicit goal pause/stop and `/clear` cancel only owned T3 work through T3 cancellation; root resource reload/reconnect preserves descendants and does not masquerade as cancellation. No native process manager, duplicate budget calculation from T3 UI totals, or second status/result ledger is introduced. See [goal policy](goal.md) for the canonical budget semantics; integrated T3 acceptance remains separate from these source-level contracts.

### Loading and verification

These are default-profile resource changes, not a T3 build, installation, generated-bridge edit, or replacement. Reload resources or restart **idle affected Pi sessions** to load them, including retained children that would otherwise run old code. Reloading a root does not hot-upgrade another running child process. Do not restart the current working thread or desktop app as a validation shortcut. Existing native Pi/Herdr paths and their settled-only reload rules are unchanged.

Focused composition checks are `pnpm test t3-role-guidance.test.ts subagent-guidance.test.ts` from the default profile. They cover full source-coupled caller/coordinator/leaf sections, inclusion/exclusion, deterministic ordering and static byte comparison. Static size is not measured cache performance. The installed-T3 integration smoke has **not yet passed** at this documentation update; these checks do not establish live lifecycle, rendered UI, question delivery, or acceptance.

## Native Pi / Herdr backend

The remaining lifecycle, surface, native question protocol, layout and command sections describe the unchanged **native** backend unless explicitly stated otherwise. Shared definitions and role-routing policy apply to both hosts; native-only arguments and Herdr controls do not become T3 capabilities.

`subagent` launches a bounded specialist assignment. Omit `surface` for normal delegation: children are visible inside Herdr by default and headless elsewhere; coordinator children inherit their coordinator's surface. Inside Herdr, select `surface: "headless"` only when the user requests it, not merely because work is parallel, unattended, or in a worktree. This is tool guidance, not a runtime authorization check. Visible launch never falls back to headless.

**Readable layout reconciliation, 2026-10-25:** Ordinary visible subagents occupy one row of at most two panes above the original full-width caller, which keeps the lower half whenever that row is present. Capacity is based on 50 terminal columns and 14 rows per pane: fewer than 100 columns allows only one agent in the row, and fewer than 50 columns or 28 total rows sends all agents to overflow instead of splitting the caller. Clean layouts compact and reassess capacity on launch and close, including moving an over-capacity row to overflow after a window shrink and returning a small team when origin space becomes available. There is no polling or process recreation.

A geometry/topology change at unchanged window size freezes that tab: existing panes stay owned, but it is not resized, subdivided, or used as a migration destination. Teams containing a pane on a frozen tab are not automatically migrated; new descendants use clean team overflow instead. Owned overflow tabs preserve manual names, and caller or unrelated tabs are never renamed. Before launch, `pane current --current` resolves a moved caller by terminal identity. Same- and cross-workspace moves update exact returned pane IDs and preserve verified terminal identities; ambiguous mutations stop without recreating processes. ## Definitions and authority

Editable profile roles live in `agents/*.md`. Built-in bare family defaults (`astra`, `sol`, `terra`, `luna`) select the latest authenticated native `openai` subscription version at launch, with no provider fallback. Explicit `provider/model` references remain exact. Trusted projects can override them through the nearest `.pi/agents/` directory. Invalid overrides disable the affected names rather than restoring a more powerful profile definition. Each filename must match its `name`.

```yaml
---
name: reader
description: Inspect local evidence
tools: [read, grep, find, ls, subagent_parent]
model: luna
effort: low
skills: []
delegates: []
---
Read the assigned evidence and report the relevant findings.
```

Required fields are `name`, `description`, and `tools`; the other fields above are optional. Tool lists accept YAML arrays or comma-separated text. `tools: []` means no model-callable tools, including no hidden parent helper. `delegates` is a separate permission list. Coordinators need explicit `subagent` and `subagent_control` tools as well as permission to commission the named leaves. Leaves cannot delegate; coordinators cannot nest. Counts are guidance, not runtime limits or queues.

All roles use native context-file discovery for the active profile and the assigned working directory's ancestor instructions. This loads applicable `AGENTS.md` files (or native fallback names), not the parent's conversation. Team Leads retain automatic skill discovery; other roles load only explicitly selected skills. Extension, prompt-template, theme, and tool restrictions are unchanged.

Authority is frozen for the conversation, including reopened turns and direct user help. Call arguments cannot widen tools or delegation. Native file tools use the assigned working directory as context, not a filesystem boundary; outside paths and symlink targets are allowed subject to normal tool behavior and Damage Control. Child workspaces cannot widen a coordinator's workspace. Native `tool_search` discovers and activates only registered, already-permitted deferred tools; loading does not widen frozen authority. Only Team Lead receives `codemode`, and its scripts remain limited to its existing tool list. Ordinary roles receive permitted native search without composition. Lifecycle tools remain model-only. Write authority follows each role's declared tools: developer implements software and can edit/write, while writer can edit/write prose-oriented artifacts. Reviewer and validator are read-only roles; they return findings through their normal results, not filesystem output.

Damage Control and session-profile metadata remain loaded. Bedrock children load accounting, with Mantle provider registration added only for Mantle models. Direct operator `!` and `!!` input uses Pi's native shell path even when the role has no model-callable shell tool. This does not add `bash` to the role, and model-issued shell calls remain subject to the frozen tool ceiling and Damage Control. These tool ceilings are **not an OS sandbox**. A shell-enabled role can mutate files unless an additional enforcement policy blocks the call; absence of native edit/write tools alone does not prevent shell mutation. Ordinary child roles do not load Onclave or Herdr process/layout tools. Team Leads have deferred `herdr_agent`, `herdr_layout`, and `herdr_pane` tools in their frozen authority; they must activate them through `tool_search` and cannot widen that authority.

## Explorer shell inspection

Explorer has native Bash and PowerShell for local and live evidence investigation, without native edit/write, codemode, or new delegation authority. Both visible and headless children receive Damage Control's inspection restriction from frozen role authority. Trusted project overrides named `explorer` remain inspection-bound; launch arguments do not select a weaker policy.

Complete established observations may run. Intentional changes to files, managed resources, configuration, or processes are blocked, including temporary or recoverable changes. Unfamiliar calls and supported scripts need an explicit observational verdict from a tool-free inspection judge; uncertainty or review failure denies. Normal script preapproval and `/dc off` cannot grant mutation permission. Protected reads and other normal Damage Control restrictions remain in force. Explorer can respond to a recoverable denial with another allowed inspection or report the concrete blocker to its parent for reassignment.

This is best effort, not an OS sandbox or zero-side-effect guarantee. Incidental client caches and server access logs are compatible with observation. Explicit operator `!`/`!!` shell input retains its native exemption. Other shell-enabled roles retain their existing normal policy and prompt boundaries. See [inspection examples and controls](damage-control-setup.md#explorer-inspection) and the [policy contract](damage-control-port.md#explorer-inspection-policy).

Definition changes take effect for newly launched children after the normal settled-only reload or a fresh session; active children are not retrofitted. Reopened follow-ups cannot weaken an already-frozen inspection restriction.

## Tools and conversations

Launch arguments include `agent`, `instructions`, optional `cwd`, `model`, `providerOverride`, `effort`, `skills`, `background`, and `surface`. Ordinary launches have no `retain` option. A permitted coordinator may select any valid existing non-root directory for a leaf, including sibling worktrees and unrelated repositories; origin and delegate checks still apply. Skills are profile skill names, not arbitrary paths. Model values may be bare model names or explicit `provider/model` references. Bare names use the profile's deterministic provider ladder: authenticated native `openai` subscription models first, then `bedrock-mantle`, then native `amazon-bedrock`. Bare Opus selects the newest AWS release as described above. Known family aliases and exact or token-aligned names are accepted; unrelated substring matches are not. Within the first provider tier containing the closest match, the lowest configured baseline token cost wins. Other providers require an explicit canonical reference. Explicit model/effort overrides take precedence over the definition. Resolved launches and status records use the canonical provider/model reference; explicit references never fall through to another provider.

- A normal nonblank final reply completes the assignment and closes its process and pane automatically. Saved conversation context remains available; no manual completion or cleanup command is needed in the normal path.
- For a follow-up, send `subagent_control` with `action: "message"`, the original `subagentId`, and new instructions. The owning runtime reopens the same saved Pi session with the original frozen role, prompt, tools, delegates, cwd, model/effort, skills, and surface. That follow-up closes on completion too. This works only while the owning runtime still has the launch context, not after reload or process restart. Use IDs for closed agents because their display names can be reused.
- `background: true` returns its ID without waiting, except for `strategist`: root and coordinator tools always launch Strategist in the foreground, overriding `background: true`. The consultation blocks its parent until the result returns, then its process exits. Existing wait interruption behavior is unchanged. This does not block other launches or enforce consultation ordering across parallel tool calls. Cancelling a foreground tool wait detaches the wait, not the child.
- `subagent_control inspect` returns records and bounded results. Text results are capped at 24,000 characters. Records distinguish assignment status/outcome, exchange identity, original assignment evidence, turn count, process state, transport state, phase, tool name, and last activity time. Activity is UI-only and never creates a model message. `subagent_control wait` explicitly reattaches to a deliberately interrupted foreground join on the same child when its result is immediately required. It is not a general monitoring mechanism for sitting on one working child until routine work finishes; those outcomes arrive automatically while the parent continues other work or returns control. Detaching reports that the assignment continues and gives the inspect/wait controls. If owned-child controls cannot see or reach a visible Herdr agent or pane, discover cross-agent recovery through `tool_search`; the Herdr skill describes that conditional path.
- `message` uses one exchange path. It defaults to `delivery: "queued"` and `interaction: "notify"`; queued messages use native steering while a child is busy, start a new exchange when idle, or reopen its saved session when closed. Set `delivery: "immediate"` only to intentionally redirect the current turn. `answer` is the compatibility adapter for a `question-answer` request and accepts `replyTo` when a request reference is needed. Root and coordinator message/answer controls return once native dispatch accepts the input, regardless of the compatibility `background` value; their `dispatch` metadata explicitly reports acceptance without claiming model receipt or assignment completion. Working children and children waiting for a parent reply remain alive and can receive these exchanges. `notify` does not request acknowledgement; `request` identifies a response-bearing exchange but does not create a general correlated request protocol.
- A parent question yields successfully and leaves the child idle with `Waiting for parent reply`; it does not run a polling tool or imply completion. The child result repeats the complete bounded question and request ID. The runtime creates the request ID and correlates a matching answer. The first parent answer or child-owned `subagent_parent` `cancel-question` action wins; late answers and cancellations report that actual resolution. Ordinary user conversation does not resolve the request, and children remain alive until the request is resolved. Unknown or stale replies are native control errors. Delivery is an origin-scoped process-local mailbox: questions are queued independently of attached foreground waits and use native queued steering for busy parents/coordinators; idle delivery starts a new turn. An already exposed question gets one concise resolution update, while an undelivered resolved question is removed. Automatic outcomes are acknowledged once per outcome, so a result already received by a model is not replayed later.
- `escalate` hands a visible child to the user, or shows a pending headless user-only prompt through the originating parent's actual UI.
- `finish` retries cleanup of settled resources without changing the completed outcome. It is not a required step after normal completion. `cancel` explicitly stops ordinary work and its owned process tree. Both release the human name only after successful cleanup; result acknowledgement is not required.

`subagent_parent`, when explicitly permitted, asks factual questions or reports genuinely partial/blocked work. Successful work should use a normal final reply, not a partial report. Blank output and successful process exit do not constitute completion. Failed work is not, by itself, a reason to retain a pane.

`/subagents` or `/subagents inspect [id]` lists the current chat's descendants. `/subagents wait <id>` waits on the same child with a **Stop waiting** control; closing it leaves the child running and preserves automatic delivery to the parent model. `/subagents cancel <id>` is direct user cancellation, including a child under user intervention. Model-driven parent control is suspended during direct user help. `/subagent-return <id>` in the parent, or `/subagent-return` in the child, explicitly hands control back. Restricted children also provide `/reload` and `/exit`.

## Progress and outcome delivery

Subagents do not install a persistent status widget. Each launch uses one default card containing `Subagent`, the assigned name, role, resolved `model[effort]`, readable local start date/time, and the prompt. Once the assignment settles, that same card adds a local `Completed` or `Failed` date/time. It does not add a separate completion or interactive card. Questions, answers, dispatches, detached waits, and automatic outcomes render as compact lifecycle or message-passing rows. IDs, exchange bookkeeping, detailed results, errors, and execution metadata remain available through native expansion and `/subagents inspect [name-or-id]` rather than appearing in the default card.

Parent-channel contact establishes liveness, not productivity. There is no inactivity cancellation, assignment timeout, automatic retry, or progress-triggered model turn. Tool arguments and reasoning are not included in progress. Cleanup errors remain available in transcript outcomes and explicit inspection.

Completion, failure and factual questions reach the parent model automatically. An attached foreground model wait receives its tool result; background/detached outcomes use native queued steering while the originating parent is busy and a follow-up when it is idle. A question mailbox notification does not wait for an unrelated attached foreground wait and never aborts active work or crosses origins. Busy/inactive origins retain outcomes without transcript polling or delivery into another chat. Coordinator leaves use the authenticated held parent-event/application channel for prompt outcome delivery and journal acknowledgement. Direct follow-up input does not consume an unread outcome; journal acknowledgement or an explicit read acknowledges only the represented exchange. A coordinator remains alive while commissioned children or their unread outcomes remain; normal final settlement follows its subsequent response. If it fails or is cancelled first, outstanding outcomes go to the originating orchestrator with an explicit notice. User-only approval prompts always go to the originating user's UI, not a coordinator's factual-answer tool. Outcome delivery is not an acknowledgement request and does not generate automatic receipt chatter.

The question mailbox is process-local and is not durable across restart or parent recreation; it has no Onclave protocol, broker, service, or deployment dependency.

Native RPC `agent_end` carries an aggregate message array and can exceed 1 MiB after an otherwise successful assignment. RPC frames now have a separate 16 MiB bound and a growing, bounded frame buffer; the authenticated application channel stays at 256 KiB and final text stays at 24,000 characters. Oversized/incomplete frames report event type and byte counts without echoing payloads, then settle owned cleanup. Initial provider/prompt rejection is observed explicitly. This is bounded support for large native events, not unlimited output.

## Visibility and lifetime

Run the existing Herdr setup from the lasting checkout as described in [Herdr setup](herdr.md). The runtime verifies that `local.pi` uses that profile's repository bootstrap before opening a pane. Do not link a disposable worktree into production. Background creation should preserve the user's currently focused pane, tab and workspace, not assume the caller is focused. Plugin creation uses `--no-focus`. Herdr 0.9.0 lacks upward plugin splits and a non-focusing swap: initial placement swaps the new child above the caller, then restores the pane observed immediately before the swap if focus still points to the caller. A subsequent observed user focus change is left alone. Restoration uses the public exact-pane focus API and is not atomic; a brief focus change or a concurrent switch in the final check/restore window remains possible. No layout replay or caller-process replacement is used.

Before placement, the layout reconciles tracked child panes against both the caller and agents workspaces and stops using disappeared panes as split anchors. Cleanup accepts an already-absent owned pane without closing unrelated panes. A live-list failure remains an error, not permission to forget ownership.

Each child application and visible-child host now holds one authenticated process-local parent-event request for its consumer role. Parent commands, nested outcomes, and host-stop events wake that request immediately; acknowledgements make command and outcome delivery level-triggered and at most once where previously guaranteed. The active application and host no longer send 200 ms and 100 ms parent-query loops. Visible activity is reported only when its model/tool state changes. Native editor and PTY input, origin ownership, intervention/handback, cleanup, and parent-loss behavior remain unchanged.

A held request has no ordinary 10-second deadline and reconnects after a connection failure with up to three attempts and 250 ms then 500 ms backoff. Session replacement, child exit, parent teardown, and transport revocation abort outstanding waits. Explicit parent rejection and received stop responses remain immediate. Mutating requests, bootstrap, acknowledgements, activity reports, and final turns are not implicitly replayed. Exhausted retries preserve the existing parent-loss shutdown/user-intervention behavior. Diagnostics report request kind, connection failure category and host stop reason without endpoints, authentication tokens or message payloads. This process-local channel is not durable and does not prove attached-client keyboard behavior or the cause of the September 22 mass exits; memory limits are unchanged.

The bootstrap hosts native Pi through exact argv and inherited terminal handles, without a shell wrapper. A per-launch host owns the actual child process handle. Authenticated process-local loopback messages carry questions, delegation, replies, and control; Herdr state and terminal text are not completion evidence. Visible-child registration is checked through exact Herdr pane/agent membership, matching session identity, and lifecycle state; an accepted bootstrap API report alone is not proof because Herdr may acknowledge a queued report that terminal-state rules ignore. Results are captured and owned processes settled before immediate pane closure. Cleanup does not wait for zoom restoration.

Operators do not run `/reload` while subagents are active. The existing reload path is supported only after child conversations and owned resources have settled; active-child reload teardown, migration, and recovery are unsupported and outside this cleanup correction. Source edits do not upgrade an already-running operator session. `/clear` remains the clean-session reset, while ordinary completion and intervention semantics apply outside explicit reload.

Outside explicit reload, same-process chat changes preserve children under the existing origin-scoped lifecycle. Native `session_shutdown` also accompanies session switches and is not treated as process exit; it must not reset the shared runtime. An explicit settled-only `/reload` replaces the runtime without migrating active children, carrying pending/inert outcomes and only currently live name reservations. Released names belonging to historical children are not seeded. Background results remain bound to their originating chat: they steer that conversation while it is busy, wait in the runtime while it is inactive, and use journal-event acknowledgement to prevent repeat delivery. Results are not delivered into whichever chat happens to be active. There is no durable runtime registry or parent recreation after process exit. Newly launched children do persist metadata-only `subagent-lineage` entries in their native session JSONL: version, own session ID, role, immediate parent session ID, and root orchestrator session ID. The runtime supplies this automatically for direct and coordinator-launched children, without model-facing parameters. Authenticated startup reports associate runtime child IDs with native session IDs and files; these identities are distinct. Parent-visible records use `subagentId` (also exposed as legacy `id`) for `subagent_control`; `sessionId` is the native Pi identity used by `session_messages` and native session/analytics operations. The native `sessionId` is included only after the child identity handshake reports it, so an earlier launch response may omit it and must not infer it. Reload does not duplicate the entry for the same session. Historical sessions without records remain unclassified. Entries follow Pi's native persistence lifecycle: a fresh session is not written to disk until its first assistant message, so a child that exits before that boundary may have no searchable session file.

Discover `log_analytics` through `tool_search` using `subagent session lineage`, then use `operation: "session_lineage"` with a native `sessionId` to look up recorded ancestors and descendants. This is historical attribution, not live process status or permission to control/resume descendants. No plan association, execution tracking, or separate registry is added.

Closing the parent attempts ordinary child cleanup and reports unresolved process or pane resources before exit. Visible children under acknowledged direct user intervention stay open and show **Parent unavailable**; the user can continue directly or exit. Headless children do not remain waiting after their parent disappears. User-help state has a temporary per-launch marker for the host's parent-loss handling; it is removed when the child exits and is not restart recovery. Permission-dialog Allow/Deny input resolves that prompt only. Ordinary direct conversation input stays native: idle input starts a parent-coordinated turn, and busy input follows Pi's selected steering or follow-up behavior without taking ownership, clearing parent messages, or requiring handback. Explicit `subagent_control escalate` is the persistent intervention control, with `/subagent-return` for handback. Out-of-role model tool calls remain blocked with their reason but do not terminate the turn, so the child can recover with an allowed action. Genuine terminating native tool errors preserve the tool name and bounded actual reason on both child surfaces; a later valid final reply clears recoverable tool errors. Successful question yields and intentional redirections are not failures.

Assignment outcome and resource cleanup are separate. The first terminal assignment result, outcome, error, instructions, and timing are preserved as original-assignment evidence. Later reopened follow-ups have their own exchange identity and current result, so follow-up work, failure, or cleanup does not overwrite the original result. Inspection distinguishes active follow-up, completed follow-up, and closed resources; historical records without the added fields remain readable. Each origin has a reusable bounded pool of 64 unique first names, followed by the existing surname and numeric-suffix overflow. A name is a control alias only for its current reservation owner; once released, historical children remain addressable by UUID or prefix, not by their old name. Names stay reserved while a child has open owned resources or is user-owned, and are released only after settlement and successful resource cleanup. A completed or cancelled assignment may retain a cleanup error when process or pane closure was not proven. Independent children are still attempted, and the owner remains available for a later cleanup attempt. `/clear` reports unresolved cleanup but still enters the clean session; it skips an immediately requested source reload when that reload cannot retire the existing owner. Successful cleanup and name release are idempotent, do not repeat result delivery, and keep user-owned visible children excluded by the existing quit intervention contract. If pane closure succeeds but subsequent layout adjustment fails, the pane remains recorded as closed and the error remains available for inspection. Cleanup retries only the remaining owned resources, rather than trying to close the released pane again. A visible launch that fails before creating a pane or authenticated host is finalized without a phantom running process.

## Roles, guidance, and councils

The roles are `explorer`, `developer`, `writer`, `reviewer`, `validator`, `researcher`, `advisor`, `strategist`, `steward`, `integrator`, `teamlead`, and `council`. For authorized `/do-it` closeout, the orchestrator dispatches Integrator after the task commit from the recorded parent checkout; it owns local merge and cleanup under its isolated plan-integration skill and returns a typed outcome with evidence. `--no-merge` skips dispatch. The manifest travels in a runtime-stripped assignment envelope rather than a closeout field in the ordinary subagent tool schema. For ordinary/direct closeout, the orchestrator retains user questions, final reporting, and push/deployment authorization. Prepared Herdr runs instead use the narrow `closeout_successor` launch/inspect/message/release path, not ordinary `subagent` retention: a named Integrator starts in the recorded parent checkout in the same live tab, under an independent launch-owned host. Its conditional prompt replaces parent-only question/report instructions with native operator input and final reporting, preserving the same role tools, model/effort, local manifest and no-delegation boundary. It publishes `INTEGRATION READY` after integration and metadata with the worktree still present; release follows explicitly authorized orchestrator-only obligations. The runtime retires the exact origin gracefully and the successor observes exit before cleanup. It stays available after its final report. Pre-retirement blockers keep both panes/worktree; post-delivery retirement/removal failures report `CLEANUP PENDING` and the exact retained path. No push/deployment, branch deletion, generic detach, broad terminal authority, rollback, or parent recreation is granted. Ordinary parent-loss, intervention, layout and pane-cleanup behavior is unchanged. Writer is a flexible prose author, not a fixed artifact-specific workflow: describe the artifact, audience, purpose, supplied evidence or intent, desired style or structure, scope, and limits in the assignment as useful, and select applicable skills there. These are brief suggestions, not required fields. The parent owns dispatch and correlates/integrates results unless synthesis is explicitly assigned. Use writer when prose authorship is the delegated outcome; do not assign filesystem output to reviewer or validator, or repeat an established review solely to materialize its synthesis. The orchestrator is the primary model interacting with the user; role names, running subagents, and selected model/effort values are separate concepts. Developer and writer have native edit/write tools; developer is the software implementation role and writer focuses on prose artifacts. Developer, reviewer, and validator have shell tools. Reviewer and validator use shell commands only for inspection and checks; their no-edit/no-autofix instructions are policy boundaries, not shell sandboxes.

Consult Strategist before executing implementation plans or when user-authorized work is suited to parallel subagents or a Team Lead. For a standalone job, work directly unless the user explicitly requests a handoff or delegation conserves orchestrator context; those two handoffs skip the orchestrator's Strategist consultation. An explicit single-agent plan handoff also skips that consultation without changing the Team Lead's own Strategist-first workflow. When the user requests delegation while continuing another discussion, launch the requested agent in the background and continue the discussion. Individual assignments and temporarily serial stages remain available within an authorized multi-agent decomposition. Strategist defaults to Sol low; use Astra low when its decision spans several systems, has competing interpretations, or follows repeated failed assignments. Strategist cannot use Luna below high effort; runtime validation rejects weaker overrides. This is recommendation-only, not an approval gate. Strategist advises on bounded assignments, prerequisite order, roles, and model/effort choices using observable inputs and failure evidence. It cannot dispatch or edit. Shared guidance also permits one bounded stronger-family retry after an attempted but unsolved assignment with working inputs and tools; crashes, timeouts, missing prerequisites, environment failures, and unresolved user decisions do not establish that condition.

Steward performs post-implementation triage: consult it when a reviewer or validator agent reports findings about implemented work and you need to assess whether additional work is warranted. Supply the requested outcome, completed work, findings, and proposed follow-up. Do not consult Steward before starting requested implementation, including user-authorized fixes from a code review, or send it implementation plans, task decomposition, or the orchestrator's own investigation. Handle evidence-proved corrections directly and reuse its assessment for the same finding. Steward assesses whether proposed corrections are necessary, optional, or scope drift; it does not develop implementation plans or approve implementation. It may recommend a user question, deferral, or closeout. If sent planning, initial investigation, or pre-implementation assessment, it identifies the mismatch and returns without performing that assessment. Findings do not automatically authorize new requirements, audits, subsystems, or acceptance checks. Steward defaults to Luna high, allows Luna high or xhigh, and has no automatic larger-model retry. Selecting Sol or Astra for Steward requires a concrete justification and user approval. This restriction is specific to the model selection, not ordinary Luna consultation. Offline prompt and definition checks do not prove that Steward prevents review churn.

The orchestrator sees a generated catalog of all resolved roles. Coordinators see only their frozen permitted delegates, and Strategist sees only roles its caller may dispatch. Catalog visibility does not add dispatch authority. Trusted project overrides and disabled definitions are reflected when the catalog is composed. Child prompts and catalogs are frozen at launch, so definition changes require a new child; profile source changes require the normal settled-only `/reload` boundary.

Assign at most one named plan task per leaf worker; a Team Lead may coordinate several assignments. Strategist treats each named task as an upper boundary, not an assignment. It identifies independently verifiable outcomes before selecting workers and separates them, keeping supporting tests with the behavior they verify. Shared-file ownership calls for sequential assignments rather than bundling. Distinct design decisions, implementation mechanisms, platform variants, migration or preservation behavior, status reporting, and broad acceptance scenarios do not become one assignment merely because a plan groups them. Each recommendation briefly explains why implementation and validation form one bounded outcome; an unclear explanation means split further. Strategist recommends one worker for a bounded outcome, direct parallel workers for independent outcomes, or a Team Lead when ongoing dependency coordination or integration helps, naming that responsibility. Luna is for bounded implementation with settled interfaces and one primary result. Sol is for coupled design, state transitions, configuration preservation, or integration across multiple mechanisms; higher effort does not compensate for excessive scope. Direct execution remains preferable when delegation adds no value. Strategist actively looks for parallel work, separates shared prerequisites from independent implementation, and recommends corrections to unnecessary plan dependencies rather than treating listed order as dependency order. Its advice groups Start now, Start after prerequisites, and Parent-owned actions, with task outcomes, roles/model/effort, write ownership, completion evidence, and exact prerequisite results. Empty sections may be omitted and direct execution needs only a brief recommendation. This is adaptable prose, not a parsed schema, approval step, runtime gate, or automatic scheduler. The parent owns dispatch and integration; ready independent work runs concurrently with disjoint write ownership. Guidance is up to four Team Leads, eight leaves per lead, or twelve direct workers where coordination adds no value. Councils require an explicit user request. See the council workflow below.

### Councils

The default is three independent openings, one focused rebuttal that reopens the same members through follow-up messages, and synthesis covering strongest arguments, changed positions, disagreements, and evidence gaps. Councils do not force agreement or implementation.

The [council role](../agents/council.md) adapts review mechanics from [Theo's tstack council skill](https://github.com/t3dotgg/tstack/blob/main/skills/council/SKILL.md): a common brief and reviewed state, known-fix/check preparation for code audits, evidence-backed findings, explicit unavailable-member reporting, review-round accounting, and a summary the parent can use in a PR description. Members remain non-writing; the parent owns fixes and PR updates. A post-fix review is a fresh assignment, not the same-state rebuttal, and does not start an automatic review loop. Requested scores are optional reporting, not approval criteria. Explicitly non-blocking members do not delay synthesis; missing coverage remains visible.

Role model/effort defaults, tools, and delegate authority remain unchanged. Project-aware Opus preferences apply before the orchestrator selects a harness, not by changing a Pi model alias. Named selections are honored only through supported routes, with no silent substitution. ccyl remains an orchestrator-owned external-client route, not a Pi council member's authority bypass.
