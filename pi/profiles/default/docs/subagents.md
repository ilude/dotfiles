# Subagents

`subagent` launches a bounded specialist assignment. Omit `surface` for normal delegation: children are visible inside Herdr by default and headless elsewhere; coordinator children inherit their coordinator's surface. Inside Herdr, select `surface: "headless"` only when the user requests it, not merely because work is parallel, unattended, or in a worktree. This is tool guidance, not a runtime authorization check. Visible launch never falls back to headless.

## Definitions and authority

Editable profile roles live in `agents/*.md`. Built-in bare family defaults (`astra`, `sol`, `terra`, `luna`) select the latest authenticated Codex version at launch, with no provider fallback. Explicit `provider/model` references remain exact. Trusted projects can override them through the nearest `.pi/agents/` directory. Invalid overrides disable the affected names rather than restoring a more powerful profile definition. Each filename must match its `name`.

```yaml
---
name: reader
description: Inspect local evidence
tools: [read, grep, find, ls, subagent_parent]
model: luna
effort: low
skills: []
delegates: []
---
Read the assigned evidence and report the relevant findings.
```

Required fields are `name`, `description`, and `tools`; the other fields above are optional. Tool lists accept YAML arrays or comma-separated text. `tools: []` means no model-callable tools, including no hidden parent helper. `delegates` is a separate permission list. Coordinators need explicit `subagent` and `subagent_control` tools as well as permission to commission the named leaves. Leaves cannot delegate; coordinators cannot nest. Counts are guidance, not runtime limits or queues.

All roles use native context-file discovery for the active profile and the assigned working directory's ancestor instructions. This loads applicable `AGENTS.md` files (or native fallback names), not the parent's conversation. Team Leads retain automatic skill discovery; other roles load only explicitly selected skills. Extension, prompt-template, theme, and tool restrictions are unchanged.

Authority is frozen for the conversation, including retained turns, reload, and direct user help. Call arguments cannot widen tools or delegation. Native file tools use the assigned working directory as context, not a filesystem boundary; outside paths and symlink targets are allowed subject to normal tool behavior and Damage Control. Child workspaces cannot widen a coordinator's workspace. The restricted `tool_search` only describes already-permitted tools; it cannot activate more.

Damage Control and session-profile metadata remain loaded. Bedrock children load accounting, with Mantle provider registration added only for Mantle models. Direct operator `!` and `!!` input uses Pi's native shell path even when the role has no model-callable shell tool. This does not add `bash` to the role, and model-issued shell calls remain subject to the frozen tool ceiling and Damage Control. These tool ceilings are **not an OS sandbox**. A shell-enabled role can mutate files. Children do not load Onclave or general Herdr process/layout tools.

## Tools and conversations

Launch arguments include `agent`, `instructions`, optional `cwd`, `model`, `effort`, `skills`, `background`, `surface`, and `retain`. A permitted coordinator may select any valid existing non-root directory for a leaf, including sibling worktrees and unrelated repositories; origin and delegate checks still apply. Skills are profile skill names, not arbitrary paths. Model values may be bare model names or explicit `provider/model` references. Bare names use the profile's deterministic provider ladder: authenticated `openai-codex` subscription models first, then `bedrock-mantle`, then native `amazon-bedrock`. Known family aliases and exact or token-aligned names are accepted; unrelated substring matches are not. Within the first provider tier containing the closest match, the lowest configured baseline token cost wins. Other providers require an explicit canonical reference. Explicit model/effort overrides take precedence over the definition. Resolved launches and status records use the canonical provider/model reference; explicit references never fall through to another provider.

- A normal nonblank final reply completes the assignment automatically. No manual completion command is needed.
- `retain: true` keeps the conversation and process available for follow-ups.
- `background: true` returns its ID without waiting, except for `strategist`: root and coordinator tools always launch Strategist in the foreground and non-retained, overriding `background: true` and `retain: true`. The consultation blocks its parent until the result returns, then its process exits. Existing wait interruption behavior is unchanged. This does not block other launches or enforce consultation ordering across parallel tool calls. Cancelling a foreground tool wait detaches the wait, not the child.
- `subagent_control inspect` returns records and bounded results. Text results are capped at 24,000 characters. Records distinguish assignment status/outcome, exchange identity, original assignment evidence, turn count, process state, transport state, phase, tool name, and last activity time. Activity is UI-only and never creates a model message. `subagent_control wait` explicitly reattaches to a deliberately interrupted foreground join on the same child when its result is immediately required. It is not a general monitoring mechanism for sitting on one working child until routine work finishes; those outcomes arrive automatically while the parent continues other work or returns control. Detaching reports that the assignment continues and gives the inspect/wait controls.
- `message` uses one exchange path. It defaults to `delivery: "queued"` and `interaction: "notify"`; queued messages use native steering while a child is busy and start a retained conversation when idle. Set `delivery: "immediate"` only to intentionally redirect the current turn. `answer` is the compatibility adapter for a `question-answer` request and accepts `replyTo` when a request reference is needed. Root and coordinator message/answer controls return once native dispatch accepts the input, regardless of the compatibility `background` value; their `dispatch` metadata explicitly reports acceptance without claiming model receipt or assignment completion. Active assignments, including `retained: false` children waiting for a parent reply, can receive these exchanges. `notify` does not request acknowledgement; `request` identifies a response-bearing exchange but does not create a general correlated request protocol.
- A parent question yields successfully and leaves the child idle with `Waiting for parent reply`; it does not run a polling tool or imply completion. The child result repeats the complete bounded question and request ID. The runtime creates the request ID and correlates a matching answer. The first parent answer or child-owned `subagent_parent` `cancel-question` action wins; late answers and cancellations report that actual resolution. Ordinary user conversation does not resolve the request, and non-retained children remain alive until the request is resolved. Unknown or stale replies are native control errors. Delivery is an origin-scoped process-local mailbox: questions are queued independently of attached foreground waits and use native queued steering for busy parents/coordinators; idle delivery starts a new turn. An already exposed question gets one concise resolution update, while an undelivered resolved question is removed. Automatic outcomes are acknowledged once per outcome, so a result already received by a model is not replayed later.
- `escalate` hands a visible child to the user, or shows a pending headless user-only prompt through the originating parent's actual UI.
- `finish` closes a settled retained conversation without changing its completed outcome. `cancel` explicitly stops ordinary work and its owned process tree. Both release the human name only after successful cleanup; result acknowledgement is not required.

`subagent_parent`, when explicitly permitted, asks factual questions or reports genuinely partial/blocked work. Successful work should use a normal final reply, not a partial report. Blank output and successful process exit do not constitute completion. Failed work is not, by itself, a reason to retain a pane.

`/subagents` or `/subagents inspect [id]` lists the current chat's descendants. `/subagents wait <id>` waits on the same child with a **Stop waiting** control; closing it leaves the child running and preserves automatic delivery to the parent model. `/subagents cancel <id>` is direct user cancellation, including a child under user intervention. Model-driven parent control is suspended during direct user help. `/subagent-return <id>` in the parent, or `/subagent-return` in the child, explicitly hands control back. Restricted children also provide `/reload` and `/exit`.

## Progress and outcome delivery

Subagents do not install a persistent status widget. Each launch uses one default card containing `Subagent`, the assigned name, role, resolved `model[effort]`, readable local start date/time, and the prompt. Once the assignment settles, that same card adds a local `Completed` or `Failed` date/time. It does not add a separate completion or interactive card. Questions, answers, dispatches, detached waits, and automatic outcomes render as compact lifecycle or message-passing rows. IDs, exchange bookkeeping, detailed results, errors, and execution metadata remain available through native expansion and `/subagents inspect [name-or-id]` rather than appearing in the default card.

Heartbeats establish contact, not productivity. There is no inactivity cancellation, assignment timeout, automatic retry, or progress-triggered model turn. Tool arguments and reasoning are not included in progress. Cleanup errors remain available in transcript outcomes and explicit inspection.

Completion, failure and factual questions reach the parent model automatically. An attached foreground model wait receives its tool result; background/detached outcomes use native queued steering while the originating parent is busy and a follow-up when it is idle. A question mailbox notification does not wait for an unrelated attached foreground wait and never aborts active work or crosses origins. Busy/inactive origins retain outcomes without transcript polling or delivery into another chat. Coordinator leaves use the existing authenticated heartbeat/application channel for outcome delivery and journal acknowledgement. Direct follow-up input does not consume an unread outcome; journal acknowledgement or an explicit read acknowledges only the represented exchange. A coordinator remains alive while commissioned children or their unread outcomes remain; normal final settlement follows its subsequent response. If it fails or is cancelled first, outstanding outcomes go to the originating orchestrator with an explicit notice. User-only approval prompts always go to the originating user's UI, not a coordinator's factual-answer tool. Outcome delivery is not an acknowledgement request and does not generate automatic receipt chatter.

The question mailbox is process-local and is not durable across restart or parent recreation; it has no Onclave protocol, broker, service, or deployment dependency.

Native RPC `agent_end` carries an aggregate message array and can exceed 1 MiB after an otherwise successful assignment. RPC frames now have a separate 16 MiB bound and a growing, bounded frame buffer; the authenticated application channel stays at 256 KiB and final text stays at 24,000 characters. Oversized/incomplete frames report event type and byte counts without echoing payloads, then settle owned cleanup. Initial provider/prompt rejection is observed explicitly. This is bounded support for large native events, not unlimited output.

## Visibility and lifetime

Run the existing Herdr setup from the lasting checkout as described in [Herdr setup](herdr.md). The runtime verifies that `local.pi` uses that profile's repository bootstrap before opening a pane. Do not link a disposable worktree into production. Background creation should preserve the user's currently focused pane, tab and workspace, not assume the caller is focused. Plugin creation uses `--no-focus`. Herdr 0.9.0 lacks upward plugin splits and a non-focusing swap: initial placement swaps the new child above the caller, then restores the pane observed immediately before the swap if focus still points to the caller. A subsequent observed user focus change is left alone. Restoration uses the public exact-pane focus API and is not atomic; a brief focus change or a concurrent switch in the final check/restore window remains possible. No layout replay or caller-process replacement is used.

Before placement, the layout reconciles tracked child panes against the live workspace and stops using disappeared panes as split anchors. Cleanup accepts an already-absent owned pane without closing unrelated panes. A live-list failure remains an error, not permission to forget ownership.

Parent polls (`host-poll`, `app-poll`, and `heartbeat`) retry socket failures up to three attempts, with 250 ms then 500 ms backoff and the existing 10-second per-request deadline. Both the host and child session use this shared transport. Explicit parent rejection and received stop responses remain immediate. Mutating requests, bootstrap, acknowledgements and final turns are not implicitly replayed. Exhausted retries preserve the existing parent-loss shutdown/user-intervention behavior. Diagnostics report request kind, connection failure category and host stop reason without endpoints, authentication tokens or message payloads. This does not prove the cause of the September 22 mass exits or change memory limits.

The bootstrap hosts native Pi through exact argv and inherited terminal handles, without a shell wrapper. A per-launch host owns the actual child process handle. Authenticated process-local loopback messages carry questions, delegation, replies, and control; Herdr state and terminal text are not completion evidence. Visible-child registration is checked through exact Herdr pane/agent membership, matching session identity, and lifecycle state; an accepted bootstrap API report alone is not proof because Herdr may acknowledge a queued report that terminal-state rules ignore. Results are captured and owned processes settled before immediate pane closure. Cleanup does not wait for zoom restoration.

Operators do not run `/reload` while subagents are active. The existing reload path is supported only after child conversations and owned resources have settled; active-child reload teardown, migration, and recovery are unsupported and outside this cleanup correction. Source edits do not upgrade an already-running operator session. `/clear` remains the clean-session reset, while ordinary retention and intervention semantics apply outside explicit reload.

Outside explicit reload, same-process chat changes preserve children under the existing origin-scoped lifecycle. Native `session_shutdown` also accompanies session switches and is not treated as process exit; it must not reset the shared runtime. An explicit settled-only `/reload` replaces the runtime without migrating active children, carrying pending/inert outcomes and only currently live name reservations. Released names belonging to historical children are not seeded. Background results remain bound to their originating chat: they steer that conversation while it is busy, wait in the runtime while it is inactive, and use journal-event acknowledgement to prevent repeat delivery. Results are not delivered into whichever chat happens to be active. There is no durable runtime registry or parent recreation after process exit. Newly launched children do persist metadata-only `subagent-lineage` entries in their native session JSONL: version, own session ID, role, immediate parent session ID, and root orchestrator session ID. The runtime supplies this automatically for direct and coordinator-launched children, without model-facing parameters. Authenticated startup reports associate runtime child IDs with native session IDs and files; these identities are distinct. Reload does not duplicate the entry for the same session. Historical sessions without records remain unclassified. Entries follow Pi's native persistence lifecycle: a fresh session is not written to disk until its first assistant message, so a child that exits before that boundary may have no searchable session file.

Discover `log_analytics` through `tool_search` using `subagent session lineage`, then use `operation: "session_lineage"` with a native `sessionId` to look up recorded ancestors and descendants. This is historical attribution, not live process status or permission to control/resume descendants. No plan association, execution tracking, or separate registry is added.

Closing the parent attempts ordinary child cleanup and reports unresolved process or pane resources before exit. Visible children under acknowledged direct user intervention stay open and show **Parent unavailable**; the user can continue directly or exit. Headless children do not remain waiting after their parent disappears. User-help state has a temporary per-launch marker for the host's parent-loss handling; it is removed when the child exits and is not restart recovery. Permission-dialog Allow/Deny input resolves that prompt only. Ordinary direct conversation input stays native: idle input starts a parent-coordinated turn, and busy input follows Pi's selected steering or follow-up behavior without taking ownership, clearing parent messages, or requiring handback. Explicit `subagent_control escalate` is the persistent intervention control, with `/subagent-return` for handback. Out-of-role model tool calls remain blocked with their reason but do not terminate the turn, so the child can recover with an allowed action. Genuine terminating native tool errors preserve the tool name and bounded actual reason on both child surfaces; a later valid final reply clears recoverable tool errors. Successful question yields and intentional redirections are not failures.

Assignment outcome and resource cleanup are separate. The first terminal assignment result, outcome, error, instructions, and timing are preserved as original-assignment evidence. Later retained follow-ups have their own exchange identity and current result, so follow-up work, failure, or cleanup does not overwrite the original result. Inspection distinguishes active follow-up, completed follow-up, completed retained availability, and closed resources; historical records without the added fields remain readable. Each origin has a reusable bounded pool of 64 unique first names, followed by the existing surname and numeric-suffix overflow. A name is a control alias only for its current reservation owner; once released, historical children remain addressable by UUID or prefix, not by their old name. Names stay reserved while a child is retained or user-owned, and are released only after settlement and successful resource cleanup. A completed or cancelled assignment may retain a cleanup error when process or pane closure was not proven. Independent children are still attempted, and the owner remains available for a later cleanup attempt. `/clear` reports unresolved cleanup but still enters the clean session; it skips an immediately requested source reload when that reload cannot retire the existing owner. Successful cleanup and name release are idempotent, do not repeat result delivery, and keep user-owned visible children excluded by the existing quit intervention contract. If pane closure succeeds but subsequent layout adjustment fails, the pane remains recorded as closed and the error remains available for inspection. Cleanup retries only the remaining owned resources, rather than trying to close the released pane again. A visible launch that fails before creating a pane or authenticated host is finalized without a phantom running process.

## Roles, guidance, and councils

The roles are `explorer`, `developer`, `reviewer`, `validator`, `researcher`, `advisor`, `strategist`, `steward`, `teamlead`, and `council`. The orchestrator is the primary model interacting with the user; role names, running subagents, and selected model/effort values are separate concepts. Only developer has native edit/write tools. Developer, reviewer, and validator have shell tools. Reviewer and validator use shell commands only for inspection and checks; their no-edit/no-autofix instructions are policy boundaries, not shell sandboxes.

Consult Strategist before executing implementation plans or when user-authorized work is suited to parallel subagents or a Team Lead. For a standalone job, work directly unless the user explicitly requests a handoff or delegation conserves orchestrator context; those two handoffs skip the orchestrator's Strategist consultation. An explicit single-agent plan handoff also skips that consultation without changing the Team Lead's own Strategist-first workflow. When the user requests delegation while continuing another discussion, launch the requested agent in the background and continue the discussion. Individual assignments and temporarily serial stages remain available within an authorized multi-agent decomposition. Strategist defaults to Sol low; use Astra low when its decision spans several systems, has competing interpretations, or follows repeated failed assignments. Strategist cannot use Luna below high effort; runtime validation rejects weaker overrides. This is recommendation-only, not an approval gate. Strategist advises on bounded assignments, prerequisite order, roles, and model/effort choices using observable inputs and failure evidence. It cannot dispatch or edit. Shared guidance also permits one bounded stronger-family retry after an attempted but unsolved assignment with working inputs and tools; crashes, timeouts, missing prerequisites, environment failures, and unresolved user decisions do not establish that condition.

Steward performs post-implementation triage: consult it when a reviewer or validator agent reports findings about implemented work and you need to assess whether additional work is warranted. Supply the requested outcome, completed work, findings, and proposed follow-up. Do not consult Steward before starting requested implementation, including user-authorized fixes from a code review, or send it implementation plans, task decomposition, or the orchestrator's own investigation. Handle evidence-proved corrections directly and reuse its assessment for the same finding. Steward assesses whether proposed corrections are necessary, optional, or scope drift; it does not develop implementation plans or approve implementation. It may recommend a user question, deferral, or closeout. If sent planning, initial investigation, or pre-implementation assessment, it identifies the mismatch and returns without performing that assessment. Findings do not automatically authorize new requirements, audits, subsystems, or acceptance checks. Steward defaults to Luna high, allows Luna high or xhigh, and has no automatic larger-model retry. Selecting Sol or Astra for Steward requires a concrete justification and user approval. This restriction is specific to the model selection, not ordinary Luna consultation. Offline prompt and definition checks do not prove that Steward prevents review churn.

The orchestrator sees a generated catalog of all resolved roles. Coordinators see only their frozen permitted delegates, and Strategist sees only roles its caller may dispatch. Catalog visibility does not add dispatch authority. Trusted project overrides and disabled definitions are reflected when the catalog is composed. Child prompts and catalogs are frozen at launch, so definition changes require a new child; profile source changes require the normal settled-only `/reload` boundary.

Assign at most one named plan task per leaf worker, splitting larger tasks further when useful; a Team Lead may coordinate several assignments. Strategist treats a named task as an upper boundary, not an assignment size: multiple independently provable outcomes become smaller assignments with specific finishes while preserving the task's requirements. Strategist recommends one worker for a bounded outcome, direct parallel workers for independent outcomes, or a Team Lead when ongoing dependency coordination or integration helps, naming that responsibility. Direct execution remains preferable when delegation adds no value. Strategist actively looks for parallel work, separates shared prerequisites from independent implementation, and recommends corrections to unnecessary plan dependencies rather than treating listed order as dependency order. Its advice groups Start now, Start after prerequisites, and Parent-owned actions, with task outcomes, roles/model/effort, write ownership, completion evidence, and exact prerequisite results. Empty sections may be omitted and direct execution needs only a brief recommendation. This is adaptable prose, not a parsed schema, approval step, runtime gate, or automatic scheduler. The parent owns dispatch and integration; ready independent work runs concurrently with disjoint write ownership. Guidance is up to four Team Leads, eight leaves per lead, or twelve direct workers where coordination adds no value. Councils require an explicit user request. Their default guidance is three independent openings, one focused rebuttal with retained member contexts, and synthesis covering strongest arguments, changed positions, disagreements, and evidence gaps. They do not force agreement or implementation.

## Checks

From the default profile:

```sh
pnpm test subagent herdr-launch.test.ts session-launch.test.ts tool-visibility.test.ts herdr-ui-prompt-state.test.ts
pnpm run typecheck
pnpm run check:runtime
```

`PI_HERDR_FOCUS_LIVE=1 pnpm test herdr-background-focus.test.ts` checks plugin-split preflight, creation and cleanup while another tab or workspace is focused, using an isolated server and inert process. This verifies server-side focus state, not an attached client's physical focus behavior.

`PI_SUBAGENT_LIVE=1 pnpm test subagent-live.test.ts` enables bounded headless model acceptance. `PI_SUBAGENT_HERDR_LIVE=1 pnpm test subagent-herdr-live.test.ts` creates a fresh isolated Herdr server/config/plugin registry and disposable Git repository for each of five focused scenarios. It separately tests visible registration/state/session through reload plus headless exclusion and cleanup, intervention/handback with retained context, Team Lead descendants, council descendants, and shutdown survival. These tests require installed Herdr, working profile model credentials, and the isolated web-tools package dependencies. They do not relink the production plugin or prove physical keyboard experience, notifications, or model reasoning quality. All five focused scenarios passed on 2026-09-14; unit tests do not prove visibility.

`PI_SUBAGENT_UX_LIVE=1 pnpm test subagent-ux-live.test.ts` runs the bounded inert geometry acceptance. Add `PI_SUBAGENT_UX_LIVE_REAL=1` to run the bundled-Pi model case; its passing result is recorded above.
