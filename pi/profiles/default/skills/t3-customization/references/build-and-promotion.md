# Build and promote the customization fork

Use the installed Hatchery controller's [worker command contract](../../../../../../modules/hatchery/runner/README.md) and the repo's [Windows cross-build recipe](../../../../../../docs/t3-code.md#windows-x64-installer-from-linux-docker). The controller coordinates; the disposable Linux VM does the work. Resolve controller access through existing site configuration and trusted SSH. Do not install packages on the controller or build on Windows.

## Build from a specific snapshot

1. Identify the source checkout, base commit, exact patch, and expected checks. Check `package.json`, `pnpm-workspace.yaml`, and the packaging scripts at that revision for Node, pnpm, Vite+, Rust, artifact names and native prerequisites. For a public upstream base, the Windows recipe takes `/input/upstream-commit` plus optional `/input/source.patch`; for commits not reachable there, transfer an explicit Git bundle with its shallow boundary if applicable. Do not send the entire checkout. Record the commit and patch SHA-256 in the artifact receipt.
2. Query `hatchery targets`; choose the configured Proxmox Linux worker. Give each attempt a unique ID, a bounded TTL and enough disk for its toolchain. Use the same ID to observe a lost provisioning reply, not a parallel duplicate. When the jobs dispatcher is absent, use the documented manual lifecycle rather than enabling a shared dispatcher just for this build.
3. Transfer the patch and recipe over the controller, then use `hatchery upload` to the owned guest. Build the Windows recipe container inside the guest with `--build-arg NODE_VERSION=<source pin>`. Run focused web and browser tests against the snapshot with fixtures; don't require personal accounts or clicks. Keep checks and packaging outputs separate so one passing does not imply the other passed.
4. Collect build exit codes, logs, installer `.exe` and CLI archive, plus digests. Check the archive contains `t3.exe` and the expected Windows architecture. Transfer the requested files to ignored `.tmp/t3code-windows-build/<run>/` on Windows and check hashes there without running the installer. Confirm Hatchery destroyed the exact allocation after outputs reached the controller. If a retrieval fails, repair retrieval on that allocation rather than rerunning the build; respect its TTL.

## Promote separately

Keep a fast-forward-only upstream mirror and a separate customization branch. A trusted sync controller should check ancestry, propose a reviewed integration PR, run candidate checks without its write credential, and stop on conflict. Sync automation was dry-run locally, not deployed. Release promotion, signing credentials, update feed identity, and dotfiles pins require an explicit decision. An unsigned package using normal T3 app identity can replace an existing install; don't call it side-by-side. If asked for Windows runtime proof, check for a ready sealed Hatchery Windows template and use an isolated clone. Archive inspection on Linux is not a Windows launch or installer smoke test.

## Verified observations

- T3 base `e396bb2e264d828977bb2dbed69b425dc272d489` with the Extension status prototype passed the production web build and nine focused tests on a 16 GiB Proxmox VM using Node `26.13.1` and pnpm `12.14.0`. The 8 GiB build exited 137 during transform; the cause was not isolated. Start comparable web or packaging runs at 16 GiB rather than repeating that failure.
- The same prototype snapshot cross-built Windows preview `0.1.10-preview.20261118.2` in Linux Docker on a disposable 16 GiB Proxmox worker using Node `26.13.1`. T3's packaging check validated 66 payload files and 24 sidecar native binaries. The unsigned NSIS installer and Windows x64 CLI ZIP were copied to Windows and matched their SHA-256 manifests. Hatchery confirmed worker destruction. Neither output was executed or installed; the build skipped its Windows-only self-check.
- The no-install ZIP for `0.1.10-preview.20261118.2` was produced by extracting the verified installer's `app-64.7z` with 7-Zip on a disposable Linux worker, without executing the installer. The first attempt exhausted the worker's 2 GiB `/tmp` tmpfs while writing the ZIP. Use disk-backed `/var/tmp` for the inputs, extraction, and output; allow at least 3 GiB free for this payload. The retry verified ZIP integrity, the Windows x64 executable and companion ASAR files, the SHA-256 after transfer, and worker destruction. `Start-T3-Preview.ps1` sets a separate `T3CODE_HOME` and Electron profile under `data/` and disables automatic updates and telemetry for the preview process. It was not launched on Windows.
- The linked recipe also records Windows runtime smoke tests on the older `e455200077ce60806a01c8f28435b58860dcfc74` build. Those results do not apply to the current preview.
