# Pi instruction composition

Use this reference when a Pi-specific prompt review needs to establish what a particular model call can see. It is a source map and inspection method, not a fixed prompt snapshot or a mandatory review process.

## Composition map

### Native system prompt and tools

Pi assembles the coding-agent system prompt in the installed `@earendil-works/pi-coding-agent` package:

- `dist/core/system-prompt.js` owns the base preamble, selected-tool summaries, generated rules, documentation pointers, project-context wrappers, skill catalog, cwd, custom sections, and section rendering.
- Tool definitions are separate model inputs. Each active tool contributes its description and parameter schema. The system-prompt tool list is only a summary. Generated rules can also come from per-tool guidelines and prompt guidelines, so inspect both the tool registration and the assembled prompt options.
- `dist/core/agent-session.js` owns per-run assembly, prompt-template and skill-command expansion, `before_agent_start` transformations, active-tool changes, conversation projection, tool results, and compaction integration.
- `dist/core/messages.js` maps coding-agent message roles into model-compatible messages. Bash execution, custom messages, branch summaries, and compaction summaries become user-role context under the conditions defined there.

`dist/core/resource-loader.js` owns discovery. It loads global context from the active agent directory and project context from the cwd and its ancestors, with the file precedence and worktree handling implemented there. It also discovers extensions, skills, prompt templates, themes, `SYSTEM.md`, and `APPEND_SYSTEM.md`, subject to settings, trust, CLI overrides, and disable flags. Do not infer the active profile from the repository cwd. Resolve it through Pi's active configuration and `getAgentDir()` behavior.

### Skills and prompt expansion

The startup skill section is a catalog, not the skill bodies. `dist/core/skills.js` formats discoverable skill names, descriptions, and paths for model selection. A body becomes conversation input only when the model reads `SKILL.md`, an explicit `/skill:name` invocation expands it, or another caller supplies it. Check `docs/skills.md` and the active skill flags before treating a discovered skill as visible.

Prompt templates are expanded before their result enters the conversation as a user message. Inspect `dist/core/prompt-templates.js`, `dist/core/agent-session.js`, and `docs/prompt-templates.md`; do not count the template file and its expanded result as two simultaneous prompt layers.

### Extensions and delegated agents

Extensions can modify prompt options or force a complete prompt in `before_agent_start`, register model-visible tools, and add messages. For this profile:

- `extensions/subagents.ts` appends caller delegation guidance generated by `lib/subagents/guidance.ts`.
- `lib/subagents/guidance.ts` composes role prompts with audience-specific delegation guidance and generated role catalogs. Catalog entries describe dispatch options; they do not themselves grant authority.
- `lib/subagents/launch.ts` starts a separate Pi process with a frozen role prompt, explicit tools and extensions, and selected skills. It disables automatic skill discovery for ordinary roles. Team Leads retain skill discovery, while explicit assigned skills are passed separately.
- `extensions/subagent-child.ts` appends the child's frozen authority and role prompt to that child's native Pi prompt. The child gets context files discovered for its assigned cwd, but it does not inherit the parent's conversation, loaded skill bodies, extension stack, or tool set merely because the parent had them.
- The assignment is its own child user message and owns task-specific facts. Parent tool results reach the child only when included in the assignment or sent later through the communication protocol. Child results return to the parent as tool-result or custom-message content according to the launch path.

Other nested model calls are separate compositions. For example, `commands/commit/reviewer.ts` builds a private agent from `commands/commit/reviewer.md`, its task, and its own tools. `lib/damage-control/judge.ts` sends its review contract and a reduced evidence projection directly through the model registry. Damage Control script review launches a restricted reviewer with a purpose-built assignment. Do not assume these calls inherit the orchestrator's complete system prompt, history, skills, or tools.

`extensions/compaction.ts` customizes summary generation through the native compaction hook, combining the history and turn prefix and adding guidance to preserve current intent, scope, authorization, decisions, evidence, pending questions, and the next action. The resulting compaction summary is later projected as model-visible conversation context; the older persisted entries remain on disk but are not all replayed after the compaction boundary.

### Messages, metadata, and UI

Classify entries by the conversion path, not by whether they appear in the transcript:

- User and assistant messages, system state, tool-result `content`, and converted custom or summary messages are model-visible.
- A custom message's `display` controls rendering, not model visibility. Its `details` are not sent to the model.
- Tool-result `details`, progress updates supplied through `onUpdate`, UI notifications, status/widgets, and entries stored with `appendEntry()` are not model-visible unless another path later copies their text into a message.
- Session metadata can affect later assembly without being a message. Conversely, terminal-hidden content can still be model-visible.

### Local assembly and provider serialization

The locally assembled system state, message list, and tool definitions are not necessarily the provider wire payload. Pi first projects coding-agent messages in `dist/core/messages.js`; the installed `@earendil-works/pi-ai` package then serializes that context in its provider implementation under `dist/api/`. Providers differ in system-message placement, tool encoding, mid-conversation tool changes, normalization, and cache controls. Inspect the selected provider converter before making claims about exact payload order, cache prefixes, or token accounting.

## Inspection method

1. Identify the exact model call: orchestrator turn, child turn, compaction, commit helper, Damage Control review, or another nested completion.
2. Resolve the active Pi package and profile at runtime. Use the documentation paths exposed by the installed Pi system prompt or package exports. Do not hardcode an installed version, store hash, model, resource inventory, or tool count.
3. Start at the call site. Record its system input, message source, active tools, provider/model, and extension hooks.
4. Trace native assembly through `system-prompt.js`, `resource-loader.js`, `agent-session.js`, and `messages.js`. Then trace profile extensions and the selected provider serializer.
5. Separate catalogs from loaded bodies, tool schemas from generated tool guidelines, assignment text from inherited context, and model-visible content from metadata or UI-only state.
6. Treat files on disk as candidates, not proof of visibility. Verify discovery, trust, disable flags, active loadout, reload/session timing, and whether a resource was already read or expanded. An edit changes later reads or reloads; it does not rewrite messages or resources already loaded into an active request or conversation.
7. Render or instrument only the affected composition when necessary. Prefer source-grounded sections and dynamic boundaries over a static full-prompt dump. State which dynamic or provider-owned portions were not observed.

## Installed documentation

Read the installed documentation completely for the affected surface, following its cross-references. The usual starting points are `docs/how-pi-works.md`, `docs/extensions.md`, `docs/skills.md`, `docs/prompt-templates.md`, `docs/message-types.md`, `docs/compaction.md`, and `docs/providers.md`, plus matching examples under the installed package's `examples/` directory. Resolve these through the installed package paths advertised by Pi rather than copying a machine-specific package-store path into durable guidance.
