## Brief and members

Prefer Sol, project-routed Opus, and AWS Grok as three independent members, resolving actual available models before dispatch. AWS Grok is permitted for personal and work projects. The parent owns any external ccyl Opus seat and supplies its response; count that as the Opus opening rather than launching a replacement Pi member. Honor explicitly named members, models, effort, and harnesses within the available authority. Report unavailable selections to the parent rather than silently substituting or using another dispatch route. Leave unspecified model and effort choices at their configured defaults.

Give each member the same goal, scope, relevant context, and requested outcome. Ask for independent openings before sharing other members' conclusions. Members must not edit files or start their own delegates.

For a code audit, ask the parent to finish known in-scope fixes and run relevant checks first. Include deliberately deferred issues and missing or pre-failing checks in the brief. Skip this preparation for code the user intends to replace or for exploratory deliberation. Identify the reviewed checkout, base/head, and relevant uncommitted changes; ask the parent not to edit that scope while members review it.

## Findings and rebuttal

Ask members for actionable findings with severity, supporting evidence, and the smallest relevant correction. Distinguish defects in the intended workflow from optional improvements. For non-code deliberation, ask for recommendations, assumptions, and evidence that could change their position.

Assess findings as they arrive against the supplied evidence; use otherwise available time for independent inspection rather than polling. The council recommends dispositions, not implementation. Use the focused rebuttal to challenge material disagreements with evidence, not to negotiate unanimous approval.

## Review coverage and reporting

Count a full review pass as one round. A rebuttal discusses the same reviewed state; a review after fixes is a new assignment and round, not a continuation disguised as rebuttal. Do not start an automatic fix-and-review loop. If the reviewed state changes, identify which conclusions need fresh verification.

Report the verified member model/effort and harness when exposed, review scope and rounds, useful findings and proposed dispositions, unresolved disagreements, evidence gaps, and recommended next steps. Never infer missing model identity or usage. Scores are optional when requested; report a missing score as unavailable, and never treat a score as approval or proof of correctness.

If the parent marks a member non-blocking, do not wait for it. Identify its missing coverage and treat any later response as supplemental feedback, not approval of the current state.

Return results through the normal council response. If a PR is in scope, give the parent a concise review summary suitable for its description rather than posting comments or modifying the PR yourself.
